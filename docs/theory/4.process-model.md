# AI駆動スパイラル開発 — Software Engineeringプロセスモデル

本ドキュメントは、System Architecture DescriptionによってSoftware System Elementへ割り当てられた責任を、Software Requirements、Software Architecture、Software Element Design、Implemented Software Elements、Integrated Softwareへ変換するStandard Processを定義する。

本方式ではAI駆動スパイラルのProcess粒度とISO/IEC/IEEEのProcess粒度を1:1対応させない。一つのStandard Processの内部で複数のISO由来Engineering Process / Activityを適用してよい。

基礎とする規格は以下である。

- ISO/IEC/IEEE 12207:2026 — Software life cycle processes
- ISO/IEC/IEEE 29148:2018 — Requirements engineering
- ISO/IEC/IEEE 42010:2022 — Architecture description
- ISO/IEC/IEEE 15289:2019 — Content of life-cycle information items

---

# 3. ソフトウェア要件定義

## 3.1 位置付け

`ソフトウェア要件定義` は、System Architecture DescriptionでSoftwareへ割り当てられた責任からSoftware Requirementsを定義し、さらにSoftware Architecture DescriptionによってSoftware構造とSoftware Requirementの責任割当を明確にするStandard Processである。

```text
ソフトウェア要件定義 Process
├─ Software Requirements Definition相当のEngineering
│   └─ SRS
├─ Architecture Definition [Software]相当のEngineering
│   └─ Software Architecture Description
├─ Executor
└─ Gate
```

この束ね方はAI駆動スパイラル独自である。

## 3.2 SRS

SRSはSoftwareが満たすべきRequirementsを表現する。

ISO/IEC/IEEE 29148:2018のSoftware Requirements Specificationの考え方を基礎とする。

少なくとも以下を扱う。

- Software functional requirements
- Software quality requirements
- Software interface requirements
- Software constraints
- Data / state requirements
- Verification criteria / consideration
- Upstream traceability

SRSはSystem全体のRequirementをそのまま複製せず、Softwareへ割り当てられた責任をSoftware Requirementとして表現する。

## 3.3 Software Architecture Description

Software Architecture Descriptionは、SRSを満たすためのSoftware構造を表現するStandard Artifactである。

Architectureを導出するEngineering責任はISO/IEC/IEEE 12207:2026のArchitecture Definition [Software]を基礎とし、Architecture Descriptionのstructure / expressionはISO/IEC/IEEE 42010:2022を基準とする。

少なくとも以下を表現する。

- Software Elements
- Element responsibilities
- relationships / dependencies
- interfaces
- architecture decisions / rationale
- Software RequirementsからSoftware Elementsへのallocation / traceability

Software Architecture DescriptionはSoftware Elementの詳細設計を表現しない。

```text
SRS Requirement
      ↓ allocation / traceability
Software Architecture Description
      ↓
Software Element
```

このdependency / relationship graphは後続の`実装` Processにおける実行順序決定へ利用できる。

## 3.4 Gate

GateはSRSとSoftware Architecture Descriptionを一体として確認する。

少なくとも以下を満たす必要がある。

- Softwareへ割り当てられた責任がSRSへ追跡可能である
- 当該Cycleで必要なSoftware Requirementsが定義・判断済みである
- Software Elementsが識別されている
- architecture-level relationship / dependency / interfaceが必要な範囲で定義されている
- Software Requirements → Software Elementsのallocation / traceabilityが存在する
- Software ArchitectureとSoftware Element Designを混同していない
- `実装` Processへ渡せる状態である

# 4. 実装

## 4.1 位置付け

`実装` はDesign DefinitionとImplementationを別々のStandard Processへ分割せず、Software Element単位で縦に反復するStandard Processである。

```text
Software Architecture Description
        ↓
Software Elements / dependency graph
        ↓

Software Element
  Design Definition
       ↓
  Software Element Design
       ↓
  Implementation
       ↓
  Implemented Software Element
       ↓
  Local Test / Static Analysis / Quality Guard
       ↺ 必要ならDesign Definitionへ戻る
```

全対象Software Elementsが完了した時点で一つの`実装` Gateを成立させる。

## 4.2 Software Element Design

Software Element Designは、Software Architecture Descriptionで識別された個々のSoftware Elementについて、Implementation可能な粒度まで具体化した設計を表現する。

ISO/IEC/IEEE 12207:2026のDesign Definition [Software Element]相当のEngineering責任を基礎とする。

必要に応じて以下を扱う。

- Internal structure
- Interface detail
- Data / state / behavior
- Sequence / interaction
- Algorithm
- Error handling
- Security mechanism
- Element-level design decisions / rationale

Software Architecture DescriptionがElement間構造を扱うのに対し、Software Element Designは個々のElement内部の実現方法を扱う。

## 4.3 Implemented Software Element

Implemented Software Elementは、Software Element Designを実装として具体化した成果物である。

ISO/IEC/IEEE 12207:2026のImplementation [Software Element]相当のEngineering責任を基礎とする。

必要に応じて以下を含む。

- Source Code
- Test Code
- Configuration
- Schema / Migration
- Build / deployment definitions
- implementation evidence

## 4.4 Software Element orchestration

Software Architecture Descriptionのdependency / relationship graphに基づいて実行順序を決定する。

```text
Software Architecture Description
        ↓
dependency / relationship graph
        ↓
ready Software Elements
        ↓
Design Definition → Implementation
```

dependencyのないSoftware Elementsは並列実行可能とする。

各Software Elementではlocal test / static analysis / Quality Guard等のfeedbackによって、必要ならDesign Definitionへ戻る。

ISO/IEC/IEEE 12207:2026はSoftware life cycle processesをsoftware systemへconcurrently / iteratively / recursivelyに、elementsへincrementally適用可能としている。ただし、この具体的なElement単位のScheduling、並列化、Gate、Quality Guard feedback loopはAI駆動スパイラル独自のorchestrationである。

## 4.5 Gate

Gateは単一のImplemented Software Elementの存在ではなく、当該Cycleで対象となる全Software Elementsをまとめて確認する。

少なくとも以下を満たす必要がある。

- 対象Software ElementsがSoftware Architecture Descriptionから識別可能である
- 各対象Software ElementにSoftware Element Designが存在する
- 各対象Software ElementにImplemented Software Elementが対応する
- DesignとImplementationのtraceabilityが存在する
- 必要なlocal test / static analysis / Quality Guardが通過している
- 未実装項目がIntegrationを妨げない状態である
- Integrationへ渡せる状態である

SRS適合性の最終判定はここで行わず、後続のQA（Verification）へ残す。

# 5. 統合

## 5.1 位置付け

`統合` は、対象Implemented Software ElementsをSoftware Architecture DescriptionおよびSoftware Element Design上のrelationship / interfaceに従って組み合わせ、QAへ渡せるIntegrated Softwareを構築するStandard Processである。

ISO/IEC/IEEE 12207:2026のIntegration Processを基礎とする。

## 5.2 Output Artifact — Integrated Software

Integrated Softwareは少なくとも以下を追跡可能にする。

- 統合対象Implemented Software Elements
- relevant relationships / interfaces
- integration evidence
- artifact references
- unresolved integration items

Integrationはspecified Software Requirementsへの適合性を最終判定しない。それはQA（Verification）の責任である。

## 5.3 Gate

- 対象Implemented Software Elementsが統合されている
- Architecture / Design上のrelevant relationships / interfacesが統合結果へ反映されている
- 統合Evidenceが追跡可能である
- QA対象として識別可能なIntegrated Softwareが存在する
- 未解決事項がQA開始を妨げない状態である

# 6. Software側Traceability

最低限以下のTraceabilityを保持する。

```text
SyRS Requirement
      ↓ allocation / traceability
System Architecture Description
      ↓
Software responsibility
      ↓
SRS Requirement
      ↓
Software Architecture Description
      ↓ allocation / traceability
Software Element
      ↓
Software Element Design
      ↓
Implemented Software Element
      ↓
Integrated Software
```

このTraceabilityによって、後続のQAではspecified Software RequirementsからIntegrated Softwareまで追跡できる。

# 7. ProcessとISO Processの関係

AI駆動スパイラルのStandard ProcessとISO由来Engineering責任は1:1対応しない。

```text
ソフトウェア要件定義
├─ SRS
└─ Software Architecture Description

Engineering responsibilities
├─ Software Requirements Definition
└─ Architecture Definition [Software]
```

```text
実装
├─ Software Element Design
└─ Implemented Software Element

Engineering responsibilities
├─ Design Definition [Software Element]
└─ Implementation [Software Element]
```

Processを束ねる単位はExecutor / Artifact(s) / Gateとしての運用責任であり、ISO Processの名前をそのまま工程名にすることではない。
