# AI駆動スパイラル開発 — Software Engineeringプロセスモデル

本ドキュメントは、System Architecture DefinitionによってSoftware System Elementへ割り当てられた責任を、Software Requirement、Software Design、Softwareへ変換する標準プロセスを定義する。

基礎とする規格は、ISO/IEC/IEEE 12207:2026、ISO/IEC/IEEE 29148:2018、ISO/IEC/IEEE 15289:2019である。

ISO/IEC/IEEE 12207:2026はSoftware Life Cycle ProcessをSystem Life Cycle Processと整合した枠組みで扱う。本方式ではそのProcess frameworkをSoftware System Elementへ再帰的に適用する。

---

# 4. Software Requirements Definition

## 4.1 位置付け

本方式の `Software Requirements Definition` は、ISO/IEC/IEEE 12207:2026の `System/Software Requirements Definition` を、System Architecture DefinitionでSoftwareへAllocationされたSystem Elementに対して適用する責任を表す名称である。

したがって、単にSyRSを詳細化するProcessではない。

中心的な問いは、

> **System ArchitectureによってSoftwareへ割り当てられた責任を満たすために、Softwareは何を満たさなければならないか**

である。

```text
SyRS
  ↓
System Architecture
  ↓
Requirement Allocation
  ↓
Software responsibility
  ↓
Software Requirements Definition
  ↓
SRS
```

## 4.2 入力

- System Architecture
- Requirement Allocation
- Softwareへ割り当てられたSystem Requirements
- Software boundary
- Software interface constraints
- Applicable quality requirements
- 既存SRS

## 4.3 責務

Process実行者は少なくとも以下を行う。

- SoftwareへAllocationされた責任をSoftware Requirementsへ変換する
- Software boundaryを明確にする
- Software functional requirementsを定義する
- Software quality requirementsを定義する
- Software external / internal interface requirementsを必要な範囲で定義する
- Data / state / error / security等の必要なSoftware requirementを定義する
- Requirementを検証可能な形で記述する
- SyRS / AllocationとのTraceabilityを保持する

## 4.4 Output Artifact — SRS

SRSはSoftwareが満たすべきRequirementsを記述するInformation Itemである。

ISO/IEC/IEEE 29148:2018のSoftware Requirements Specificationの考え方を基礎とする。

少なくとも以下を扱う。

- Software functional requirements
- Software quality requirements
- Software interface requirements
- Software constraints
- Software data / state requirements
- Verification criteria / verification consideration
- Upstream traceability

SRSはSystem全体のRequirementをそのまま複製しない。

SoftwareへAllocationされた責任だけをSoftware Requirementとして扱う。

## 4.5 Gate

- SoftwareへAllocationされた責任がすべて追跡可能である
- 必要なSoftware Requirementsが定義されている
- Requirementが検証可能である
- SyRS / Architecture / AllocationとのTraceabilityがある
- Software RequirementとDesign decisionを混同していない
- Software Designを開始できる

# 5. Software Design

## 5.1 位置付け

Software Designは、SRSで定義されたSoftware Requirementsを満たすSoftware構造と実現方法を定義する。

ISO/IEC/IEEE 12207:2026のArchitecture Definition / Design DefinitionをSoftware System Elementへ適用する責務を、本方式では `Software Design` として扱う。

中心的な問いは、

> **Software RequirementsをどのSoftware構造と設計で実現するか**

である。

## 5.2 入力

- SRS
- System Architecture
- Software boundary / allocated interfaces
- Architecture constraints
- Existing software architecture / design
- Applicable quality constraints

## 5.3 責務

Process実行者は少なくとも以下を行う。

- Software architectureを定義・更新する
- Software Elements / Components / Modulesを識別する
- RequirementをSoftware Elementsへ割り当てる
- Interfaceを定義する
- Data structure / state / behaviorを設計する
- Error handling / transaction / security mechanism等を必要に応じて設計する
- Design decisionと根拠を保持する
- SRSとのTraceabilityを保持する
- Implementationが開始可能な粒度までDesignを具体化する

## 5.4 Output Artifact — Software Design

Software Designは表現形式を固定しない。

必要に応じて以下を含む。

- Software architecture
- Module / component structure
- Interface design
- Data model / schema design
- State / behavior design
- Sequence / interaction
- Algorithm
- Error handling
- Security design
- Deployment-related design
- Requirement allocation to software elements
- Design decision / rationale

文書、Model、Diagram、Schema、Type、Testable contractなど、設計責任を十分に表現できる形式を利用してよい。

ISO/IEC/IEEE 15289:2019が示すように、Information Itemは必ずしも単一の独立文書である必要はない。本方式でも、Repository上で追跡・参照可能であれば複数形式へ分割してよい。

## 5.5 Gate

- SRSの対象RequirementにDesign上の実現責任が対応している
- Software structure / boundary / interfaceが明確である
- Implementationに必要なDesign decisionが不足していない
- Architecture constraintに違反していない
- SRS → Software DesignのTraceabilityが存在する
- 未解決の重大なDesign contradictionがない
- Implementationが開始可能である

# 6. Implementation

## 6.1 目的

Implementationは、Software Designを実行可能なSoftwareへ変換する。

ISO/IEC/IEEE 12207:2026のImplementation Processを基礎とする。

中心的な問いは、

> **Software Designを実際に動作するSoftwareとして実現できているか**

である。

## 6.2 入力

- Software Design
- SRS
- System Architecture / allocated interfaces
- Coding / quality / architecture constraints
- Existing Software

## 6.3 責務

Process実行者は少なくとも以下を行う。

- Software DesignをSoftwareへ実装する
- 必要なSource Codeを作成・更新する
- 必要なConfiguration / Schema / Migration等を作成・更新する
- Designとの整合性を維持する
- 実装単位の検証に必要なTest / static check等を整備する
- 既存Softwareへの不必要な破壊を避ける
- SRSやDesignの変更が必要な場合に上位Artifactを暗黙変更しない

## 6.4 Output Artifact — Software

Software Artifactは、当該CycleのSoftware Designを実現する実装成果物である。

必要に応じて以下を含む。

- Source Code
- Test Code
- Configuration
- Schema
- Migration
- Build definition
- Deployment definition
- Generated artifacts

ImplementationのArtifact名は `Software` とする。

Test CodeやStatic Analysis ResultはSoftwareを構成・支持するEvidenceとなり得るが、後続のVerification Resultとは区別する。

## 6.5 Implementation内の検証

Implementation Process内部でUnit Test、Type Check、Lint、Build、Review等を実施してよい。

ただし、それらはImplementationを成立させるための活動であり、後続の独立したVerification Processを置き換えない。

```text
Implementation internal checks
= Softwareを正しく構築するための局所的確認

Verification
= specified requirementsに対する適合性の評価
```

## 6.6 Gate

- 当該CycleのSoftware DesignがSoftwareへ反映されている
- Implementationに必要なlocal tests / static checksが通過している
- Build可能である
- 未解決の重大なReview問題がない
- Software DesignとのTraceabilityがある
- Verificationが開始可能なSoftware状態である

# 7. Software側Traceability

最低限以下のTraceabilityを保持する。

```text
SyRS Requirement
      ↓
Requirement Allocation
      ↓
Software responsibility
      ↓
SRS Requirement
      ↓
Software Design Element
      ↓
Software
```

このTraceabilityによって、Verificationでは「指定されたRequirementsを満たしているか」をRequirements側からSoftwareまで追跡できる。

次文書ではVerification、Validation、Feedbackを定義する。
