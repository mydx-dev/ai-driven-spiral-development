# Change Locality / Context Locality

## 1. 目的

AI駆動スパイラル開発では、要求変更が正常かつ継続的に発生する。

そのため、ソフトウェアの品質を、

> 現在の要求を満たしているか

だけでなく、

> 次の要求変更をどれだけ低コストで実施できるか

という観点から評価する。

本方式では、この変更容易性を支える概念として、

```text
Change Locality
Context Locality
```

を重視する。

---

# 2. Change Locality

Change Localityとは、

> **一つの要求変更に対して変更する必要のあるコードを局所化すること**

である。

理想的には、

```text
要求変更
↓
少数の責務
↓
少数のModule
↓
少数のTest
↓
変更完了
```

となる。

一つの要求変更によって多数のModuleを同じ理由で変更する必要がある場合、責務の分離または依存関係に問題がある可能性がある。

高凝集・疎結合は、それ自体を目的とするのではなく、

> **Change Localityを高めるための設計原則**

として扱う。

---

# 3. Context Locality

AI Agentが変更を行うためには、変更対象そのものだけでなく、

```text
既存仕様
関連責務
依存関係
既存Test
影響範囲
```

を理解する必要がある。

このとき、コードベース全体を毎回探索しなければ変更できない設計は、AIにとって高コストである。

そこで、

> **変更判断に必要なContextへ少ない探索で到達できる性質**

をContext Localityとする。

```text
Change Locality
= 変更するコードを減らす

Context Locality
= 変更するために読む情報を減らす
```

AI駆動開発では両者を重要な設計品質とする。

---

# 4. Contextは段階的に取得する

Agentは既存仕様を理解するために、最初からProduction Code全体を読まない。

抽象度の高い情報から低い情報へ、段階的に探索する。

基本的な探索順序は以下とする。

```text
Specification Index
↓
Repository Structure
↓
Dependency Structure
↓
Executable Specification Index
↓
Relevant Test
↓
Relevant Production Code
```

上位の情報だけで判断できる場合、それより下位の情報を不要に取得しない。

原則は、

> **必要になるまで詳細コードを読まない。**

である。

---

# 5. Specification Index

既存仕様を把握するために、コードそのものとは別に仕様インデックスを用意する。

例えばレイヤー単位で、

```text
Domain
Application
Presentation
Frontend
```

などの既存仕様をまとめる。

Specification IndexはProduction Codeの詳細な再記述ではない。

Agentが、

```text
何が存在するか
どの責務がどこにあるか
次にどこを調べるべきか
```

を判断するためのNavigation Indexとして扱う。

---

# 6. Executable Specification Index

Test Codeは既存Behaviorの実行可能な仕様として利用する。

ただし、既存仕様を確認するためにすべてのTest Codeを読む必要はない。

Test Runner等が持つテスト一覧取得機能を利用し、

```text
どのTest Suiteが存在するか
どのBehaviorが検証されているか
```

を低コストで一覧取得できるようにする。

Agentは、

```text
Test List
↓
Relevant Test
```

という順番で探索する。

---

# 7. Repository Structure

ファイルやModuleの配置は、コードベースの概念構造を理解するための重要なContextである。

例えば、

```text
src/
├ domain/
├ application/
├ infrastructure/
└ presentation/
```

のような構造から、

```text
どの責務が存在するか
どのレイヤーに所属しているか
```

をAgentが判断できる。

Repository Structureは木構造として取得可能な形式で保持する。

ただし、

> ファイルの配置関係

と、

> Module間の依存関係

は異なる。

依存関係は必ずしも木構造ではない。

---

# 8. Dependency Structure

Module間の依存関係はGraphとして扱う。

例えば、

```text
A → B
A → C
C → D
```

のような構造である。

Dependency StructureによってAgentは、

```text
対象Moduleが何に依存しているか
対象Moduleを何が利用しているか
変更の影響範囲
レイヤーを越えた依存
循環依存
```

などをProduction Code全体を読む前に把握できる。

Dependency Structureは、

> **AIが変更対象へ到達するためのNavigation Index**

として利用する。

---

# 9. Code Graph

Repository StructureとDependency Structureを合わせて、Agentが利用できる構造情報をCode Graphとして扱うことができる。

概念的には、

```text
Repository Tree
= 所属・配置

Dependency Graph
= 依存・影響関係
```

を持つ。

重要なのは特定の可視化ツールを使用することではない。

AgentまたはStatic Analysis Systemが、

```text
Module
Dependency
Dependent
Layer
Boundary
Cycle
```

などを機械的に取得できる形式であることを重視する。

Code Graphは人間向けの図だけとして保持しない。

可能な場合は、

```text
構造化データ
テキスト
Graph表現
```

など、Agentが直接検索・解析できる形式も提供する。

---

# 10. Code GraphはDerived Artifactとする

Code Graphを人間が手作業で更新しない。

Production Codeから再生成可能なDerived Artifactとして扱う。

```text
Source Code
↓
Static Analysis
↓
Code Graph
```

という関係を維持する。

古いCode GraphがProduction Codeより優先されてはならない。

---

# 11. Architecture Enforcement

高凝集・疎結合などのArchitecture Principleを、

> Agentへの自然言語Instructionだけ

で保証しない。

例えば、

```text
「DomainからInfrastructureへ依存しないでください」

「循環依存を作らないでください」

「PresentationからDatabaseへ直接アクセスしないでください」
```

とPromptへ書くだけでは不十分である。

AgentはInstructionを誤解したり、Context不足によって違反する可能性がある。

したがって可能なArchitecture Ruleは、

> **違反したコードを機械的に識別できる形式**

としてコードベースに保持する。

---

# 12. Static AnalysisによるArchitecture Enforcement

静的解析には複数の粒度が存在する。

## File / Syntax Level

一般的な静的解析によって、

```text
禁止構文
命名
型
未処理Promise
特定APIの使用
Component構造
Method構造
```

などを検証できる。

## Module / Architecture Level

一方、

```text
Layer Dependency
Module Boundary
循環依存
依存方向
Architecture上禁止されたModule間接続
```

などは、単一ファイルの構文解析だけでは十分に検証できない。

これらを保証するためには、

> **複数Module間のDependency Graphを解析できる専用のStatic Analysis**

が必要になる場合がある。

どのツールを利用するかは実装言語・Framework・Architectureによって異なる。

本方式では特定製品を標準としない。

重要なのは、

```text
Architecture Rule
↓
Machine Readable Rule
↓
Static Analysis
↓
Violation Detection
```

が成立していることである。

---

# 13. PromptではなくConstraintとして保持する

設計思想には二種類ある。

## Guideline

機械的に判定できない原則。

例えば、

```text
責務を適切に分離する
理解しやすい名前を付ける
過剰な抽象化を避ける
```

など。

これらはAgent InstructionやReviewで扱う。

## Constraint

機械的に判定可能な原則。

例えば、

```text
Domain → Infrastructureは禁止
循環依存は禁止
1 Fileに複数Componentを置かない
特定Moduleから特定Moduleへのimportは禁止
```

など。

これらはPromptではなくStatic Analysis Ruleとして保持する。

原則として、

> **機械判定可能なルールを自然言語だけで管理しない。**

---

# 14. Agent InstructionとStatic Analysisの責務

Agent Instructionは、

```text
どう設計するべきか
何を優先するか
なぜその設計思想を採用するか
```

を伝える。

Static Analysisは、

```text
何をしてはいけないか
Architecture Boundaryを越えていないか
```

を検証する。

```text
Agent Instruction
= Design Guidance

Static Analysis
= Architecture Constraint
```

として責務を分離する。

---

# 15. ArchitectureをExecutableにする

本方式ではArchitectureを文書だけとして存在させない。

Architecture Documentで定義された制約のうち、機械判定可能なものはStatic Analysis Ruleへ変換する。

```text
Architecture Document
↓
Machine Readable Constraint
↓
Static Analysis
↓
CI
```

これにより、

```text
設計思想としては正しい
しかし実装は違反している
```

という状態を継続的に検出する。

---

# 16. AI駆動開発における重要性

人間中心の開発では、Architecture Ruleを熟練Developerが暗黙知として維持できる場合がある。

Agent主体の開発では、その前提を置かない。

Agentは毎回異なるContextから作業する可能性がある。

したがって、

> **Architecture KnowledgeをAgentの記憶へ依存させない。**

コードベースそのものが、

```text
許可される依存
禁止される依存
責務境界
検証方法
```

を機械的に表現できる状態を作る。

これによってAgentが変わってもArchitectureを維持できる。

---

# 17. 最終原則

AI駆動スパイラル開発では、

```text
Specification
↓
Structure
↓
Dependency
↓
Test
↓
Code
```

の順番でContextを段階的に取得する。

同時に、

```text
Design Principle
↓
Machine Readable Constraint
↓
Static Analysis
↓
CI
```

によってArchitectureを維持する。

目的はAgentへ大量の設計文書を読ませることではない。

> **Agentが必要な情報だけを取得でき、Architectureに違反した場合はコードベース自身がそれを機械的に検出できる状態を作る。**

これをChange LocalityおよびContext Localityを支える基本原則とする。
