# AI駆動スパイラル開発におけるソフトウェア品質

## 1. 目的

AI駆動スパイラル開発では、要求・要件・設計・実装を一度確定して終了するのではなく、成果物とフィードバックをもとにサイクルを継続的に反復する。

```text
要求
↓
要件
↓
設計
↓
実装
↓
検証
↓
フィードバック
↓
次の変更
```

したがって、変更は例外ではなく、開発プロセスそのものの一部である。

この開発方式では、現在の実装が正しく動作するだけでは不十分である。

サイクルを重ねても、

1. 変更すべき箇所を容易に特定できる
2. 変更の影響範囲を把握できる
3. 変更影響を局所化できる
4. 変更内容を十分に検証できる
5. 変更後も要求された機能を正確に提供できる

状態を継続的に維持する必要がある。

そのため、AI駆動スパイラル開発では ISO/IEC 25010 の品質モデルを参照し、特に **Maintainability（保守性）** を強く要求する。

また、変更後の品質を保証するため、**Functional correctness（機能正確性）** も同時に要求する。

本開発方式では、これらの品質特性を抽象的な努力目標として扱わない。

> **品質特性に対する具体的な要件を定義し、可能なものは定量評価・静的解析・テスト・変更履歴解析などによって機械的に観測し、品質ゲートとして強制する。**

---

# 2. 品質要件の全体構造

AI駆動スパイラル開発では、変更を安全かつ継続的に行える状態を次のように捉える。

```text
変更対象を特定・理解できる
        ↓
Analysability（解析性）

変更影響を局所化できる
        ↓
Modularity（モジュール性）

変更後の振る舞いを十分に検証できる
        ↓
Testability（試験性）

変更後も要求された機能を正確に提供できる
        ↓
Functional correctness（機能正確性）

────────────────────

これらを維持しながら
安全かつ効率的に変更できる
        ↓
Modifiability（修正性）
```

ここで、Functional correctness は Maintainability の下位特性ではない。

しかし、AI駆動スパイラル開発では、

> **変更しやすいだけではなく、変更によって既存機能の正確性を損なわないこと**

が不可欠であるため、修正性を実践的に成立させるための必須品質要件として扱う。

---

# 3. 品質要件

## 3.1 Analysability（解析性）

### 要件

変更要求を受けたときに、

- どの仕様が関係するか
- どの責務が関係するか
- どの実装を変更すべきか
- どの範囲へ影響するか

を、コードベース全体を網羅的に探索せず特定できること。

また、一つの実装単位を理解するために必要な認知負荷が一定水準以下であること。

### 観測可能な要件

例として、以下を品質要件として設定できる。

```text
Cognitive Complexity <= N

Cyclomatic Complexity <= N

仕様がテストケースによってインデックス化されている

仕様 → テスト → 責務 → 実装
の対応を追跡できる

循環依存が存在しない

責務境界が明確である
```

---

## 3.2 Modularity（モジュール性）

### 要件

ソフトウェアが責務単位に適切に分割され、一つの責務に対する変更が本来無関係な責務へ不要に伝播しないこと。

そのため、

- 高凝集
- 疎結合
- 明確な公開境界
- 一方向の依存関係

を維持する。

### 観測可能な要件

例として、以下を品質要件として設定できる。

```text
LCOM <= N

TCC >= N

CBO <= N

Circular Dependency = 0

禁止されたレイヤー依存 = 0

不要な helper / 自由関数 = 0

single-use trivial function = 0

宣言クラス外から参照されない public method = 0

this を利用しない instance method = 0

不要な private method = 0

unused class member = 0

unused export = 0

God Class = 0

重複率 <= N

Temporal Coupling <= N
```

閾値 `N` は言語、プロジェクト規模、アーキテクチャ等によって異なるため、本開発方式では固定しない。

---

## 3.3 Testability（試験性）

### 要件

変更された責務について、

- 独立して試験できる
- 必要な入力を容易に与えられる
- 結果を容易に観測できる
- 外部要因を必要に応じて分離できる
- 変更によって影響を受ける仕様を十分に再検証できる

こと。

### 観測可能な要件

```text
責務単位でテスト可能である

外部I/Oを分離できる

テスト対象が多数の具体実装へ直接依存していない

テスト時に巨大な環境構築を要求しない

Cyclomatic Complexity <= N

テスト対象となる実行経路を網羅可能な水準に保つ

仕様に対応するテストケースが存在する
```

試験性はモジュール性と強く関係する。

密結合な実装では、一つの責務を試験するだけでも多数の依存先を準備する必要がある。

したがって、

```text
高い Modularity
↓
責務を独立して扱える
↓
高い Testability
```

という関係が存在する。

---

## 3.4 Functional correctness（機能正確性）

### 要件

変更後のソフトウェアが、定義された要求・仕様に対して正しい結果を提供すること。

変更容易性が高くても、変更によって既存仕様を壊すのであれば十分な品質とはいえない。

### 観測方法

機能正確性は主としてテストによって検証する。

```text
仕様
↓
テストケース
↓
実装
↓
テスト実行
↓
期待結果との一致
```

したがって、AI駆動スパイラル開発では、

> **仕様とテストケースの対応を維持すること**

を重要な品質要件とする。

変更された仕様についてテストを更新し、既存仕様について回帰テストを実行する。

---

## 3.5 Modifiability（修正性）

### 要件

既存の品質を不必要に劣化させることなく、要求された変更を安全かつ効率的に実施できること。

AI駆動スパイラル開発では、修正性を単独のメトリクスとして評価するのではなく、

```text
Analysability
+
Modularity
+
Testability
+
Functional correctness
↓
Modifiability
```

という実践的な品質モデルとして扱う。

すなわち、

> **変更対象を容易に発見でき、変更影響が局所化され、変更内容を十分に試験でき、その結果として機能正確性を維持したまま変更できる状態**

を高い修正性とする。

---

# 4. 解析性を高める実践的手法

## 4.1 Cognitive Complexity

Cognitive Complexity は、コードを人間やAIエージェントが理解する際の認知的な複雑さを観測する。

### 品質要件

```text
Cognitive Complexity <= N
```

### 検出

ESLint 等の静的解析を利用する。

例えばプロジェクトで `15` を上限とする場合、

```text
Cognitive Complexity > 15
→ Lint failure
```

とする。

### 問題

認知的複雑度が高い場合、

- 条件関係を理解しにくい
- 変更影響を把握しにくい
- 変更すべき箇所を判断しにくい

ため、解析性が低下する。

---

# 5. Cyclomatic Complexity

Cyclomatic Complexity は、制御フロー上の独立した経路の複雑さを観測する。

### 品質要件

```text
Cyclomatic Complexity <= N
```

### 影響

Cyclomatic Complexity が高い場合、

```text
実行経路が増える
↓
理解すべき状態が増える
↓
Analysability 低下

+

検証すべき経路が増える
↓
Testability 低下
↓
検証漏れの可能性増加
↓
Functional correctness を損なうリスク増加
```

となる。

したがって、複雑度は解析性だけでなく、試験性および機能正確性にも影響する品質指標として扱う。

---

# 6. 複雑度制約による副作用

AIエージェントに複雑度の上限だけを与えると、次の局所最適が発生しやすい。

```text
Cognitive / Cyclomatic Complexity が高い
↓
Lint failure
↓
処理を細かい関数へ分割
↓
一度しか呼ばれない小関数が大量生成
↓
各関数単体の Complexity は低下
↓
Lint 通過
```

複雑度を下げること自体は正しい。

問題は、**処理量を基準として分割し、責務を基準として分割していないこと**である。

そのため、

> **複雑度は分割の必要性を示し、モジュール性は分割方法を制約する。**

という関係で品質要件を組み合わせる。

---

# 7. single-use trivial function

### 兆候

次の条件を同時に満たす関数。

```text
同一ファイル内のみで利用
AND
fan-in <= 1
AND
LOC <= N
AND
Complexity <= N
```

### 原因

複雑度を下げるためだけに手続きの断片を関数化している。

### 問題

関数単位のComplexityは下がるが、

- 責務が分散する
- 処理を理解するために複数関数を追跡する必要がある
- 仕様上の責務とコード境界が一致しなくなる

可能性がある。

### 対処

その処理が独立した変更理由を持たないなら、呼び出し元へ戻す。

独立した変更理由を持つなら、その責務を表すクラス・モジュール等へ移動する。

### 品質ゲート

```text
single-use trivial function > 0
→ error
```

---

# 8. 不要な自由関数・helper

### 要件

責務の所属先が不明確な自由関数を原則として作らない。

特にバックエンド等で、

```ts
function calculateOrderTotal(order: Order) {}
```

のような処理が存在する場合、

> この振る舞いは誰の責務か

を先に判断する。

Order 自身の責務なら、

```ts
order.total();
```

とする。

独立した変更理由を持つなら、その責務を表す別オブジェクトへ配置する。

### 検出

- ESLint AST rule
- TypeScript Compiler API
- ts-morph

などを利用する。

名称が `helper`、`util` であるかどうかは本質ではない。

**名前ではなく構造を検出する。**

---

# 9. 内部参照しかされない public API

### 兆候

public method として定義されているが、宣言クラス外から一度も参照されていない。

### 原因

例えば、

```text
private method 禁止
↓
AIエージェントが public に変更
↓
Lint 通過
```

といった品質ゲート回避によって発生する。

### 検出

TypeScript symbol reference を解析する。

```text
public method
↓
全referenceを取得
↓
宣言class外からのreference = 0
↓
error
```

### 対処

独立した責務でなければ呼び出し元へ統合する。

独立した責務なら適切な責務境界へ移す。

---

# 10. `this` を利用しない instance method

### 兆候

```ts
class User {
  normalize(value: string) {
    return value.trim();
  }
}
```

### 検出

ESLint:

```js
"@typescript-eslint/class-methods-use-this": "error"
```

### 原因

処理の所属を考えず、とりあえず既存クラスへ配置している。

### 対処

- 独立させる必要がなければ元の処理へ統合する
- 独立した責務なら別の責務境界へ移動する

---

# 11. private method

AI駆動スパイラル開発では、private method の大量生成も責務分割を隠蔽する可能性がある。

```ts
class OrderService {
  execute() {}

  private validate() {}
  private normalize() {}
  private prepare() {}
  private calculate() {}
}
```

この構造では、一見するとpublic APIは小さい。

しかし内部では手続き的な処理分割が大量に存在する可能性がある。

そのため利用側プロジェクトの設計方針によっては、

```text
private method = 0
```

を品質要件として採用できる。

ただし、これはISO/IEC 25010そのものの要求ではなく、モジュール性を維持するための実装上の制約である。

---

# 12. LCOM

### 目的

クラス内メソッドとインスタンス状態の関連性を観測する。

### 品質要件

```text
LCOM <= N
```

### 兆候

異なるメソッド群が互いに別々の状態だけを操作している。

```text
method A → field X
method B → field Y
method C → field Z
```

### 原因

複数の責務が同じクラスへ混在している可能性がある。

### 対処

状態とメソッドのまとまりを確認し、異なる変更理由を持つものを適切な責務へ分離する。

LCOMが基準内であることは高凝集を保証しない。

あくまで低凝集の兆候を観測する。

---

# 13. TCC

### 品質要件

```text
TCC >= N
```

### 目的

同一クラス内のメソッド同士がどの程度関連しているかを観測する。

### 兆候

TCC が低い場合、互いに関連の薄いメソッド群が一つのクラスへ混在している可能性がある。

### 対処

状態・振る舞い・変更理由のまとまりを再確認する。

---

# 14. CBO

### 品質要件

```text
CBO <= N
```

### 目的

一つのクラスがどれだけ多数の他クラスと結合しているかを観測する。

### 問題

CBO が高いほど、一つの変更について考慮すべき外部責務が増える。

これは、

- Modularity
- Analysability
- Testability

のすべてに影響する。

```text
結合対象増加
↓
変更影響範囲増加
↓
Modularity 低下

+

理解すべき依存増加
↓
Analysability 低下

+

テスト準備対象増加
↓
Testability 低下
```

### 対処

責務境界と依存方向を見直し、本当に必要な契約だけへ依存する。

---

# 15. 循環依存

### 品質要件

```text
Circular Dependency = 0
```

### 検出

- dependency-cruiser
- ArchUnitTS
- その他依存グラフ解析

### 問題

循環依存は、

- 責務境界を曖昧にする
- 単独変更を困難にする
- 影響分析を困難にする
- 独立試験を困難にする

ため、Modularity、Analysability、Testability のすべてを低下させる。

### 対処

依存方向を一方向へ整理する。

---

# 16. レイヤー依存方向

### 品質要件

設計上禁止された依存を存在させない。

```text
Forbidden Dependency = 0
```

例えば、

```text
presentation
↓
application
↓
domain
```

という方向を採用する場合、

```text
domain → presentation
```

を静的解析で拒否する。

### 検出

- dependency-cruiser
- ArchUnitTS

---

# 17. God Class

### 兆候

例えば、

```text
method count 高
+
field count 高
+
CBO 高
+
LCOM 悪化
+
TCC 低下
+
WMC 高
```

などが同時に発生する。

### 品質要件

```text
God Class = 0
```

### 対処

単にファイルを分割しない。

```text
状態
+
その状態を操作する振る舞い
+
変更理由
```

を基準として責務を分離する。

---

# 18. 未使用・過剰な公開境界

## unused class member

```text
unused class member = 0
```

## unused export

```text
unused export = 0
```

### 検出

Knip 等を利用する。

### 理由

不要な公開境界やメンバーは、

- 責務境界を不明確にする
- 将来の依存点を増やす
- 解析対象を増やす

ため、不要なものを残さない。

---

# 19. 重複コード

### 品質要件

```text
Duplication <= N
```

### 検出

jscpd 等の clone detection を利用する。

### 注意

重複を発見したからといって、

```text
共通helperへ切り出す
```

ことを自動的な改善方法としてはならない。

まず、

> その処理は誰の責務か

を判断する。

同じ責務なら、その責務境界へ集約する。

---

# 20. Temporal Coupling

### 目的

静的構造だけでなく、実際の変更履歴から変更の局所性を観測する。

```text
変更1: A + B
変更2: A + B
変更3: A + B
```

のように、A と B が高頻度で同時変更される場合、隠れた責務分散・結合が存在する可能性がある。

### 測定

- Git history analysis
- Code Maat
- temporal coupling analysis

### 品質要件

```text
Temporal Coupling <= N
```

または閾値超過時に設計レビューを要求する。

---

# 21. 仕様のインデックス化

解析性を高めるため、現在の仕様をコードベース全体から探索する必要がない状態を作る。

AI駆動スパイラル開発では、テストケース一覧を仕様の索引として利用する。

Vitest では、

```bash
vitest list
```

によってテストケース一覧を取得できる。

テスト名を仕様として記述し、一覧をドキュメントとして保存することで、

```text
仕様変更
↓
仕様インデックスを参照
↓
該当テストを特定
↓
責務を特定
↓
実装を特定
```

という導線を作る。

### 品質要件

```text
すべての検証可能な仕様が
テストケースとして索引化されている
```

これにより、仕様変更のたびにコードベース全体を網羅的に検索する必要性を低減する。

---

# 22. テストケース構造とモジュール性

モジュール性が高く、仕様単位の責務境界が明確であれば、テストケースの構造も自然に整理される。

例えば、

```text
Order
├─ 商品を追加できる
├─ 商品を削除できる
└─ 合計金額を計算できる

DiscountPolicy
├─ 通常割引を適用できる
└─ キャンペーン割引を適用できる

TaxPolicy
└─ 税額を計算できる
```

となる。

反対に、

- 一つの仕様が多数のテストファイルへ分散する
- テストケースを責務単位に分類できない
- 同じ仕様変更で多数の無関係なテストを修正する
- `Utils` や巨大な `Service` のテストに多数の仕様が混在する

場合、Modularity または Analysability に問題が存在する可能性がある。

したがって、

> **テストケース一覧そのものも責務設計を観測する一つの成果物となる。**

---

# 23. 機能正確性の検証

変更後には必ずテストを実行し、機能正確性を検証する。

```text
変更前仕様
+
今回の変更仕様
↓
Test Suite
↓
すべて成功
↓
Functional correctness の確認
```

テストが存在するだけでは不十分である。

変更によって影響する仕様がテストによって表現され、再実行可能である必要がある。

---

# 24. 品質特性間の関係

品質特性は独立して扱わない。

例えば、CBOは単にModularityだけの指標ではない。

```text
CBO 増加
├─ 変更波及増加
│   → Modularity 低下
│
├─ 理解対象増加
│   → Analysability 低下
│
└─ テスト依存増加
    → Testability 低下
```

Cyclomatic Complexityも、

```text
Cyclomatic Complexity 増加
├─ 理解困難
│   → Analysability 低下
│
└─ 検証経路増加
    → Testability 低下
        ↓
    Functional correctness を
    検証しきれない可能性
```

と複数の品質特性へ影響する。

したがって、メトリクスと品質特性を単純な1対1対応として扱わない。

---

# 25. 品質要件一覧

プロジェクトでは、例えば次の品質要件を設定できる。

| 品質特性                                 | 品質要件                                 |
| ---------------------------------------- | ---------------------------------------- |
| Analysability                            | Cognitive Complexity <= N                |
| Analysability / Testability              | Cyclomatic Complexity <= N               |
| Analysability                            | 仕様がテストケースとして索引化されている |
| Modularity                               | LCOM <= N                                |
| Modularity                               | TCC >= N                                 |
| Modularity / Analysability / Testability | CBO <= N                                 |
| Modularity                               | Circular Dependency = 0                  |
| Modularity                               | Forbidden Layer Dependency = 0           |
| Modularity                               | single-use trivial function = 0          |
| Modularity                               | internal-only public method = 0          |
| Modularity                               | `this` を利用しない instance method = 0  |
| Modularity                               | private method = 0 ※採用する場合         |
| Modularity                               | unused class member = 0                  |
| Modularity                               | unused export = 0                        |
| Modularity                               | God Class = 0                            |
| Modularity                               | Duplication <= N                         |
| Modularity                               | Temporal Coupling <= N                   |
| Testability                              | 責務単位で独立してテスト可能             |
| Functional correctness                   | 全仕様に対応するテストが成功する         |

---

# 26. 品質ゲート

機械的に観測可能な要件は品質ゲートとして強制する。

```text
AIエージェント
↓
実装
↓
品質ゲート
├─ Lint
├─ static analysis
├─ software metrics
├─ architecture test
├─ dependency analysis
├─ test
└─ history analysis
↓
違反
├─ YES → 修正
└─ NO  → 成果物確定
```

AIエージェントが品質原則を理解していることを前提にしない。

> **品質要件を満たさない実装を成果物として確定できない環境を作る。**

---

# 27. pre-commit と CI

軽量な品質ゲートは実装直後に実行する。

```text
pre-commit
├─ ESLint
├─ Complexity
├─ 禁止構造
├─ unused detection
└─ 軽量な dependency check
```

より広範囲な検証はCIで実行する。

```text
CI
├─ Test
├─ LCOM / TCC / CBO
├─ Architecture Test
├─ Circular Dependency
├─ Layer Dependency
├─ Duplication
└─ Functional correctness
```

Temporal Coupling のように変更履歴を必要とするものは、定期品質分析として実行してもよい。

---

# 28. メトリクスの位置付け

品質メトリクスは、

> 良い設計であることを証明するスコア

として扱わない。

例えば、

```text
LCOM <= N
=
高凝集である
```

とは判断しない。

正しくは、

```text
LCOM > N
↓
低凝集である可能性
↓
成果物を一度停止
↓
責務設計を確認
```

である。

CBO、TCC、Complexityその他の指標についても同様である。

---

# 29. AIエージェントによる局所最適を防ぐ

単一の品質指標だけを強制してはならない。

AIエージェントは、その指標を満たす最短の実装へ最適化する可能性がある。

代表例:

```text
Complexity 上限
↓
小関数大量生成
↓
Complexity 改善
↓
Modularity 悪化
```

そのため、

```text
Complexity
+
Cohesion
+
Coupling
+
Testability
+
Functional correctness
```

を同時に観測する。

一つの品質特性を改善するために、別の品質特性を悪化させる実装を許容しない。

---

# 30. まとめ

AI駆動スパイラル開発では、変更を継続的に行うことそのものが開発方式の前提である。

したがって、保守性、とりわけ、

- Analysability
- Modularity
- Testability
- Modifiability

を強く要求する。

さらに、変更によって既存機能の正確性を損なわないため、

- Functional correctness

を同時に要求する。

本開発方式では、修正性を実践的に次のように捉える。

```text
高い Analysability
+
高い Modularity
+
高い Testability
+
維持された Functional correctness
↓
高い Modifiability
```

これらを維持するため、

- Cognitive Complexity
- Cyclomatic Complexity
- LCOM
- TCC
- CBO
- 循環依存
- レイヤー依存
- single-use trivial function
- internal-only public API
- unused API
- God Class
- duplication
- temporal coupling
- テストケースによる仕様索引
- テスト結果

などを客観的に観測する。

重要なのは特定の数値を達成することではない。

> **変更対象を容易に分析でき、変更影響を局所化でき、十分に検証でき、機能正確性を維持したまま継続的に変更できる状態を、機械的な品質要件によって維持すること**

を、AI駆動スパイラル開発におけるソフトウェア品質の基本方針とする。
