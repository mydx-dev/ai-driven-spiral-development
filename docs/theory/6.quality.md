# AI駆動スパイラル開発におけるソフトウェア品質

## 1. 目的

AI駆動スパイラル開発では、要求・要件・設計・実装を一度確定して終了するのではなく、成果物とフィードバックをもとにサイクルを継続的に反復する。

```text
要求
↓
要件
↓
設計
↓
実装
↓
検証
↓
フィードバック
↓
次の変更
```

したがって、変更は例外ではなく、開発プロセスそのものの一部である。

この開発方式では、現在の実装が正しく動作するだけでは不十分である。

サイクルを重ねても、

1. 変更すべき箇所を容易に特定できる
2. 変更の影響範囲を把握できる
3. 変更影響を局所化できる
4. 変更内容を十分に検証できる
5. 変更後も要求された機能を正確に提供できる

状態を継続的に維持する必要がある。

そのため、AI駆動スパイラル開発では ISO/IEC 25010 の品質モデルを参照し、特に **Maintainability（保守性）** を強く要求する。

また、変更後の品質を保証するため、**Functional correctness（機能正確性）** も同時に要求する。

本開発方式では、これらの品質特性を抽象的な努力目標として扱わない。

> **品質特性に対する具体的な要件を定義し、可能なものは定量評価・静的解析・テスト・変更履歴解析などによって機械的に観測し、品質ゲートとして強制する。**

---

# 2. 品質要件の全体構造

AI駆動スパイラル開発では、変更を安全かつ継続的に行える状態を次のように捉える。

```text
変更対象を特定・理解できる
        ↓
Analysability（解析性）

変更影響を局所化できる
        ↓
Modularity（モジュール性）

変更後の振る舞いを十分に検証できる
        ↓
Testability（試験性）

変更後も要求された機能を正確に提供できる
        ↓
Functional correctness（機能正確性）

────────────────────

これらを維持しながら
安全かつ効率的に変更できる
        ↓
Modifiability（修正性）
```

Functional correctness は Maintainability の下位特性ではない。

しかし本開発方式では、

> **変更しやすいだけではなく、変更によって既存機能の正確性を損なわないこと**

が不可欠であるため、修正性を実践的に成立させる必須品質要件として扱う。

---

# 3. Analysability（解析性）

## 要件

変更要求を受けたときに、

- どの仕様が関係するか
- どの責務が関係するか
- どの実装を変更すべきか
- どの範囲へ影響するか

を、コードベース全体を網羅的に探索せず特定できること。

また、一つの実装単位を理解するために必要な認知負荷を一定水準以下に保つ。

## 観測可能な要件

```text
Cognitive Complexity <= N

Cyclomatic Complexity <= N

仕様がテストケースによって索引化されている

仕様 → テスト → 責務 → 実装
の対応を追跡できる

Circular Dependency = 0
```

---

# 4. Modularity（モジュール性）

## 要件

ソフトウェアが責務単位に適切に分割され、一つの責務に対する変更が本来無関係な責務へ不要に伝播しないこと。

そのため、

- 高凝集
- 疎結合
- 明確な公開境界
- 一方向の依存関係
- 処理とその所属責務の対応

を維持する。

新しい処理境界を作ること自体をモジュール化とは扱わない。

> **新しい関数・メソッド・クラス等の処理境界を作る場合、その処理がなぜその型・モジュール・責務に所属するのか説明できなければならない。**

特に重要なのは、複雑度とモジュール性の役割を分離することである。

> **複雑度は分割の必要性を示し、モジュール性は分割方法を制約する。**

複雑度を下げるためだけに手続き断片へ分割してはならない。

責務境界に関する詳細は [責務境界の品質理論](./6.1.responsibility-boundary.md) で定義する。

## 観測可能な要件

```text
LCOM <= N

TCC >= N

CBO <= N

Circular Dependency = 0

Forbidden Dependency = 0

God Class = 0

Duplication <= N

Temporal Coupling <= N
```

これらの値は良い設計を証明するものではない。

責務設計が悪化している可能性を検出するセンサーとして扱う。

---

# 5. Testability（試験性）

## 要件

変更された責務について、

- 独立して試験できる
- 必要な入力を容易に与えられる
- 結果を容易に観測できる
- 外部要因を必要に応じて分離できる
- 変更によって影響を受ける仕様を十分に再検証できる

こと。

```text
高い Modularity
↓
責務を独立して扱える
↓
高い Testability
```

## 観測可能な要件

```text
責務単位でテスト可能である

外部I/Oを分離できる

テスト対象が多数の具体実装へ直接依存していない

Cyclomatic Complexity <= N

仕様に対応するテストケースが存在する
```

---

# 6. Functional correctness（機能正確性）

変更後のソフトウェアが、定義された要求・仕様に対して正しい結果を提供すること。

```text
仕様
↓
テストケース
↓
実装
↓
テスト実行
↓
期待結果との一致
```

したがって、

> **仕様とテストケースの対応を維持すること**

を重要な品質要件とする。

変更された仕様についてテストを更新し、既存仕様について回帰テストを実行する。

---

# 7. Modifiability（修正性）

修正性は単独のメトリクスとして評価しない。

```text
Analysability
+
Modularity
+
Testability
+
Functional correctness
↓
Modifiability
```

すなわち、

> **変更対象を容易に発見でき、変更影響が局所化され、変更内容を十分に試験でき、その結果として機能正確性を維持したまま変更できる状態**

を高い修正性とする。

---

# 8. Complexity

## Cognitive Complexity

コードを人間やAIエージェントが理解する際の認知的複雑さを観測する。

```text
Cognitive Complexity <= N
```

値が高い場合、

- 条件関係を理解しにくい
- 変更影響を把握しにくい
- 変更すべき箇所を判断しにくい

ため、Analysability が低下する。

## Cyclomatic Complexity

制御フロー上の独立した実行経路を観測する。

```text
Cyclomatic Complexity <= N
```

値が高い場合、

```text
実行経路増加
├─ 理解対象増加
│   → Analysability 低下
│
└─ 検証経路増加
    → Testability 低下
        ↓
    Functional correctness の
    検証漏れリスク増加
```

となる。

---

# 9. Cohesion と Coupling

## LCOM

クラス内メソッドとインスタンス状態の関連性を観測する。

```text
LCOM <= N
```

高い値は、複数の責務が同一クラスへ混在している兆候となる。

## TCC

同一クラス内のメソッド同士の関連性を観測する。

```text
TCC >= N
```

低い値は、互いに関連の薄い振る舞いが一つのクラスへ混在している兆候となる。

## CBO

一つの責務がどれだけ多数の他責務と結合しているかを観測する。

```text
CBO <= N
```

CBO の増加は、

- Modularity
- Analysability
- Testability

のすべてへ影響する。

---

# 10. Dependency

## 循環依存

```text
Circular Dependency = 0
```

循環依存は、

- 責務境界を曖昧にする
- 単独変更を困難にする
- 影響分析を困難にする
- 独立試験を困難にする

ため禁止する。

## レイヤー依存方向

設計上禁止された依存を存在させない。

```text
Forbidden Dependency = 0
```

例えば、

```text
presentation
↓
application
↓
domain
```

という方向を採用する場合、

```text
domain → presentation
```

を品質ゲートで拒否する。

---

# 11. God Class

次のような複数指標の組み合わせによって巨大責務を観測する。

```text
method count 高
+
field count 高
+
CBO 高
+
LCOM 悪化
+
TCC 低下
+
WMC 高
```

品質要件は、

```text
God Class = 0
```

とする。

単にファイルを分割するのではなく、

```text
状態
+
その状態を操作する振る舞い
+
変更理由
```

を基準として責務を分離する。

---

# 12. 重複コード

```text
Duplication <= N
```

重複を検出したからといって、

```text
共通helperへ切り出す
```

ことを自動的な改善方法としてはならない。

先に、

> その処理は誰の責務か

を判断する。

---

# 13. Temporal Coupling

静的構造だけでなく、変更履歴から変更の局所性を観測する。

```text
変更1: A + B
変更2: A + B
変更3: A + B
```

のようにAとBが継続的に同時変更される場合、隠れた責務分散や結合が存在する可能性がある。

```text
Temporal Coupling <= N
```

または閾値超過時に設計レビューを要求する。

---

# 14. 仕様のインデックス化

現在の仕様をコードベース全体から探索しなくてもよい状態を作る。

例えばVitestでは、

```bash
vitest list
```

によってテストケース一覧を取得できる。

```text
仕様変更
↓
仕様インデックス
↓
該当テスト
↓
責務
↓
実装
```

という導線を維持する。

テストケース一覧そのものも、責務設計を観測する成果物となる。

---

# 15. 品質特性間の関係

品質メトリクスを品質特性と単純な1対1対応にしない。

例えばCBOは、

```text
CBO 増加
├─ 変更波及増加
│   → Modularity 低下
│
├─ 理解対象増加
│   → Analysability 低下
│
└─ テスト依存増加
    → Testability 低下
```

と複数の品質特性へ影響する。

Complexityについても同様である。

---

# 16. 品質メトリクスの位置付け

メトリクスは、

> 良い設計であることを証明するスコア

として扱わない。

例えば、

```text
LCOM <= N
=
高凝集である
```

とは判断しない。

正しくは、

```text
LCOM > N
↓
低凝集である可能性
↓
成果物確定を停止
↓
責務設計を確認
```

である。

各メトリクスは設計劣化を観測するセンサーである。

---

# 17. 品質ゲート

機械的に観測可能な品質要件は品質ゲートとして強制する。

```text
実装主体
├─ AIエージェント
└─ 人間
↓
実装
↓
品質ゲート
↓
違反
├─ YES → 修正
└─ NO  → 成果物確定
```

AIエージェントが品質原則を理解していることも、人間の実装者が常に正しい設計判断を行うことも前提にしない。

> **品質要件を満たさない実装を成果物として確定できない環境を作る。**

具体的な機械ゲートの構成については [Quality Guard](./6.2.quality-guard.md) で定義する。

---

# 18. まとめ

AI駆動スパイラル開発では、

```text
高い Analysability
+
高い Modularity
+
高い Testability
+
維持された Functional correctness
↓
高い Modifiability
```

という品質モデルを採用する。

特にModularityについては、

> **複雑度は分割の必要性を示し、モジュール性は分割方法を制約する。**

という関係を重視する。

重要なのは特定のメトリクス値を達成することではない。

> **変更対象を容易に分析でき、変更影響を局所化でき、十分に検証でき、機能正確性を維持したまま継続的に変更できる状態を、機械的な品質要件によって維持すること**

を、AI駆動スパイラル開発におけるソフトウェア品質の基本方針とする。
