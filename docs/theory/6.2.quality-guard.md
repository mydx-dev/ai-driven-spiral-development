# Quality Guard

## 1. 目的

Quality Guard は、ソフトウェア品質に関する観測可能な要件を機械的に強制する仕組みである。

AI駆動スパイラル開発では、

> **品質要件を満たさない実装を成果物として確定できない状態**

を作る。

Quality Guard はAIエージェントだけを対象としない。

人間の実装者にも同じ品質ゲートを適用する。

---

# 2. 基本構造

```text
実装主体
├─ AIエージェント
└─ 人間
↓
実装
↓
Quality Guard
↓
違反
├─ YES → 修正
└─ NO  → 成果物確定
```

意味的な責務判断そのものを完全に機械化する必要はない。

観測可能な構造を複数の独立したセンサーで検査する。

---

# 3. Guard の構成

例えば次のように構成できる。

```text
Quality Guard
│
├─ AST Guard
│  ├─ private / protected method
│  ├─ static method
│  ├─ static-only class
│  ├─ top-level free function
│  └─ local named / arrow helper
│
├─ Reference Guard
│  ├─ internal-only public method
│  ├─ unused member
│  ├─ unused export
│  └─ unused file
│
├─ Cohesion Guard
│  ├─ LCOM
│  └─ TCC
│
├─ Coupling Guard
│  ├─ CBO
│  ├─ Circular Dependency
│  └─ Forbidden Dependency
│
├─ Complexity Guard
│  ├─ Cognitive Complexity
│  ├─ Cyclomatic Complexity
│  └─ WMC
│
├─ Structure Guard
│  ├─ method count
│  ├─ field count
│  └─ God Class
│
├─ Duplication Guard
│
├─ Test Guard
│
└─ Suppression Guard
```

一つのツールですべてを検出する必要はない。

---

# 4. AST Guard

ソースコードの構文木から、責務境界の逃避に利用される構造を検出する。

対象例:

```text
private / protected method

static method

static-only class

top-level free function

local named function

変数へ格納した local arrow helper
```

実装手段として、

- ESLint custom rule
- TypeScript Compiler API
- ts-morph
- その他AST解析

を利用できる。

---

# 5. Reference Guard

宣言された境界が実際にどこから利用されているかを解析する。

例えば、

```text
public method
↓
symbol reference解析
↓
宣言class外からのreference = 0
↓
error
```

とする。

対象例:

```text
internal-only public method = 0

unused class member = 0

unused export = 0

unused file = 0
```

KnipやTypeScript symbol解析等を利用できる。

---

# 6. Cohesion Guard

責務内部のまとまりを観測する。

```text
LCOM <= N

TCC >= N
```

LCOMやTCCが基準を満たすからといって高凝集を証明するわけではない。

閾値を超えた場合に、

```text
責務混在の可能性
↓
成果物確定停止
↓
設計確認
```

とする。

---

# 7. Coupling Guard

責務間の結合を観測する。

```text
CBO <= N

Circular Dependency = 0

Forbidden Dependency = 0
```

利用可能な手段として、

- dependency-cruiser
- ArchUnitTS
- 独自dependency graph解析

などがある。

---

# 8. Complexity Guard

処理の理解・検証が困難になる水準を超えないようにする。

```text
Cognitive Complexity <= N

Cyclomatic Complexity <= N

WMC <= N
```

ただしComplexity Guardだけを適用すると、

```text
Complexity違反
↓
小さなhelper大量生成
↓
Complexityのみ改善
```

という局所最適が発生する。

そのためResponsibility Boundary Guardと必ず組み合わせる。

---

# 9. Structure Guard

責務を分割できないことを理由として巨大classへ処理を集中させる逃避を防止する。

例えば、

```text
method count <= N

field count <= N

God Class = 0
```

を設定する。

God Class は単一指標ではなく、

```text
method count
+
field count
+
CBO
+
LCOM
+
TCC
+
WMC
```

などの複合条件として検出する。

---

# 10. single-use trivial boundary

処理をComplexity回避のためだけに細分化する構造を観測する。

例:

```text
local only
AND
fan-in <= 1
AND
LOC <= N
AND
Complexity <= N
```

を満たした場合に違反候補とする。

ただし、

```text
fan-in = 1
```

だけで禁止してはならない。

単一利用でも独立した責務は成立し得る。

---

# 11. Duplication Guard

```text
Duplication <= N
```

を設定する。

例えばjscpd等のclone detectionを利用できる。

ただし重複検出後に自動的に共通helperへ切り出してはならない。

責務境界を先に判断する。

---

# 12. Test Guard

変更後のFunctional correctnessを検証する。

```text
変更
↓
Test Suite
↓
全仕様成功
↓
成果物確定
```

また、テストケース一覧を仕様インデックスとして利用できる。

```bash
vitest list
```

などによって、

```text
仕様
↓
テスト
↓
責務
↓
実装
```

を追跡可能にする。

---

# 13. Suppression Guard

品質ルールを実装コード側から自由に無効化できてはならない。

例えば、

```ts
// eslint-disable-next-line ...
```

を実装者が自由に追加できる状態では、

```text
品質違反
↓
inline suppression
↓
成果物確定
```

が成立する。

そのため、

```text
inline suppression = 0
```

を原則とする。

ESLintでは例えば中央設定で、

```js
export default [
  {
    linterOptions: {
      noInlineConfig: true,
      reportUnusedDisableDirectives: "error",
    },
  },
];
```

のような方針を採用できる。

例外が必要な場合は各ソースコードへ分散させず、中央設定で管理する。

```text
例外が必要
↓
中央設定変更
↓
レビュー
↓
例外適用
```

とする。

---

# 14. static method の例外

static methodを原則禁止する場合でも、正当な構造は存在する。

例:

- Factory Method
- Named Constructor
- フレームワーク契約として要求されるstatic API

例外は名称だけで判断しない。

例えばFactory Methodであれば、

```text
static method
↓
return type解析
↓
declaring class自身を生成・返却
```

など、可能な限り構造的に証明する。

フレームワーク上必要な例外は中央設定で管理する。

---

# 15. レイヤー別の適用

Quality Guardはプロジェクト全体へ無条件に同じルールを適用しない。

例えばクラス指向のBackendでは、

```text
top-level free function = 0

private method = 0

static method = 0

local helper = 0
```

を採用できる。

一方Reactでは、

```tsx
export function UserCard() {}
```

や、

```ts
export function useUser() {}
```

自体が責務境界となる。

したがって、

```text
Frontend Component / Hook
→ top-level functionを許可

Backend Domain / Application
→ top-level functionを原則禁止
```

のように設計モデル単位でルールを切り替える。

---

# 16. 設定の概念例

クラス指向のバックエンドレイヤーであれば、概念的には次のような設定を持てる。

```yaml
responsibility-boundary:
  private-or-protected-method:
    severity: error

  instance-method-without-this:
    severity: error

  internal-only-public-method:
    severity: error

  static-method:
    severity: error
    exceptions:
      - kind: factory-method
        proof: return-type-assignable-to-declaring-class

      - kind: framework-contract
        proof: centrally-configured-contract

  static-only-class:
    severity: error

  top-level-free-function:
    severity: error

  local-named-helper:
    severity: error

  single-use-trivial-boundary:
    severity: error
    conditions:
      fan-in-max: 1
      loc-max: N
      complexity-max: N

  unused-member:
    severity: error

  unused-export:
    severity: error

  unused-file:
    severity: error

  inline-suppression:
    severity: error
```

React等ではoverrideする。

```yaml
overrides:
  - files:
      - "frontend/components/**"
      - "frontend/hooks/**"

    responsibility-boundary:
      top-level-free-function:
        severity: off
```

この形式自体を標準とするものではない。

---

# 17. 利用可能な実装手段

Quality Guardは特定ツールへ依存しない。

例えば、

- ESLint
- TypeScript Compiler API
- ts-morph
- Knip
- dependency-cruiser
- ArchUnitTS
- jscpd
- Git history analysis
- 独自AST解析
- 独自メトリクス解析

などを組み合わせられる。

重要なのはツールではなく、

```text
品質要件
↓
観測方法
↓
機械ゲート
↓
違反時に成果物確定停止
```

という構造である。

---

# 18. pre-commit

軽量で高速な品質ゲートは実装直後に実行する。

```text
pre-commit
├─ Lint
├─ Complexity
├─ AST Guard
├─ unused detection
└─ 軽量dependency check
```

これによりGitHub等へpushする前に構造劣化を検出できる。

---

# 19. CI

より広範囲な解析はCIで実行する。

```text
CI
├─ Test
├─ LCOM / TCC / CBO
├─ Architecture Test
├─ Reference Analysis
├─ Circular Dependency
├─ Forbidden Dependency
├─ Duplication
└─ Functional correctness
```

変更履歴を必要とするTemporal Coupling等は、定期品質分析として実行してもよい。

---

# 20. センサーの相互補完

Quality Guardでは、一つのルールを回避すると別のルールで検出される構造を作る。

```text
Complexityを回避
→ trivial boundary

private禁止を回避
→ internal-only public

this未使用を回避
→ static method

static禁止を回避
→ local helper

分割そのものを拒否
→ God Class / Complexity

無意味な別classへ移動
→ unused / cohesion / coupling
```

単一ルールではなく、

> **複数の独立したセンサーを重ねる**

ことが重要である。

---

# 21. Quality Guard の限界

Quality Guardは意味的な設計の正しさを証明しない。

```text
LCOM 良好
TCC 良好
CBO 良好
Complexity 良好
```

であっても、ドメイン上の責務境界が誤っている可能性はある。

Quality Guardの役割は、

> **意味的設計を機械へ完全委任すること**

ではない。

> **明らかに不適切な構造を成果物として確定させず、実装主体へ再設計を要求すること**

である。

---

# 22. まとめ

Quality Guardは、品質原則を単なる指針として終わらせないための仕組みである。

```text
意味的品質原則
+
機械的に観測可能なセンサー
+
成果物確定を停止するゲート
```

を組み合わせる。

AIエージェントや人間の設計能力にはばらつきが存在する。

そのため、

> **実装主体が常に正しい判断を行うことではなく、品質を満たさない成果物を確定できない環境を作ること**

をQuality Guardの基本方針とする。
