# AI駆動スパイラル開発 — 標準プロセスモデル

## 1. 標準プロセスモデルの位置付け

AI駆動スパイラル開発は、特定のプロセス構成を必須としない。

本方式が定義する中心的な構造は、

```text
プロセス実行者
      │
      │ アーティファクトを生成・更新
      ↓
意味的完了
      │
      │ Event
      ↓
Spiral
      │
      ↓
プロセスゲート
      │
      │ アーティファクトを観測
      ↓
構造的完了
      │
      ↓
次のプロセス
```

というプロセス制御モデルである。

どのようなプロセスを配置するかは、この制御モデルとは独立している。

本ドキュメントおよび後続のプロセスドキュメントで定義するプロセス群は、AI駆動スパイラル開発をソフトウェア開発へ適用するための**標準プロセスモデル**である。

標準プロセスモデルは、大きく次の3つに分類する。

```text
準備
↓
開発
↓
フィードバック
```

これらは推奨される標準構成であり、AI駆動スパイラル開発の必須構成ではない。

開発対象、組織、品質要求、法的要求、運用方式などに応じて、プロセスを追加、削除、置換、分割、統合してよい。

例えば、

```text
セキュリティレビュー
法務レビュー
性能検証
データ移行
インフラ構築
承認
監査
```

などの独自プロセスを追加することができる。

独自プロセスについても、

- プロセス実行者
- アーティファクト
- 意味的完了
- プロセスゲート
- 構造的完了

という基本構造に従うことで、同一のSpiral上へ組み込むことができる。

したがって、

> **AI駆動スパイラル開発が標準化するのはプロセスの種類ではなく、異なるプロセスを安全に接続し、自律的に進行させるための制御構造である。**

標準プロセスモデルは、その制御構造をソフトウェア開発へ適用するためのデフォルト構成として提供する。

---

# 2. 要求定義プロセス

## 2.1 目的

要求者が被要求者に対して期待する状態変化を、要求として明確にする。

要求は、その抽象度を固定しない。

例えば、以下はいずれも要求として扱う。

```text
「営業活動の情報共有を効率化したい」

「顧客一覧画面に過去の商談履歴を表示してほしい」

「営業担当は自分の営業情報だけを閲覧でき、
管理者はすべて閲覧でき、
メンターは担当営業の案件情報を閲覧できるようにしてほしい」
```

要求の粒度は、業務レベルから仕様に近い具体的な状態まで許容する。

---

## 2.2 要求の定義

要求とは、

> **要求者が被要求者に対して、要求対象を現在の状態から期待する状態へ変化させることを期待すること**

である。

要求は、少なくとも以下の要素によって構成する。

### 要求者

要求を行う主体。

本開発方式では、例えば、

- クライアント
- 顧客
- 発注者
- 開発依頼者

などが該当する。

### 被要求者

要求を受ける主体。

例えば、

- 開発者
- 開発受託会社
- 受託者

などが該当する。

### 要求対象

要求者が状態変化を期待する対象。

要求対象の種類や抽象度は固定しない。

例えば、

- 業務
- 業務フロー
- 情報
- 機能
- 画面
- 操作
- 権限
- 既存仕様

などが要求対象となり得る。

### 現在状態

要求対象が現在どのような状態にあるか。

### 期待状態

要求対象がどのような状態になることを要求者が期待しているか。

---

## 2.3 要求状態の客観性

期待状態は、客観的に観測可能であることが望ましい。

例えば、

```text
「顧客一覧画面に過去の商談履歴が表示される」
```

は成果物から比較的直接観測できる。

一方、

```text
「営業情報の共有を効率化したい」
```

のように、要求定義時点では客観的な到達判定が困難な要求も許容する。

このような要求を、要求として不適格とはしない。

要求定義では、要求者の期待を過度にシステム仕様へ変換しないことを優先する。

要求到達を直接観測することが難しい場合は、後続の要件定義によって、要求到達のために必要となる条件を導出する。

---

## 2.4 入力

要求者から取得した情報。

例えば、

- 会話
- ヒアリング記録
- メール
- メッセージ
- フィードバック
- 前サイクルの検収結果

など。

---

## 2.5 プロセス実行者の責務

プロセス実行者は、入力された情報から要求を生成・更新する。

責務は以下とする。

- 要求者を特定する
- 被要求者を特定する
- 要求対象を特定する
- 現在状態を記録する
- 期待状態を記録する
- 要求を一意に識別可能にする
- 要求の発生源を追跡可能にする

要求の抽象度を無理に統一しない。

また、要求を実現する具体的なシステム仕様や技術的解決方法まで、このプロセスで決定する必要はない。

---

## 2.6 アーティファクト

### 要求

各要求について、少なくとも以下を持つ。

- 要求識別子
- 要求対象
- 現在状態
- 期待状態
- 要求の発生源
- 対象サイクル

必要に応じて、

- 補足情報
- 背景
- 関連する既存要求
- 前サイクルからの変更理由

を含めてよい。

---

## 2.7 アーティファクトの制約

要求には、実装方法を必要以上に含めない。

ただし、要求者自身が具体的な仕様を要求している場合は、それを要求としてそのまま記録してよい。

例えば、

```text
「一覧画面に商談履歴を表示してほしい」
```

という要求を、

```text
「営業情報を確認しやすくしたい」
```

と意図的に抽象化し直す必要はない。

要求者が実際に期待している状態を保持することを優先する。

---

## 2.8 プロセスゲート

プロセスゲートは、要求アーティファクトの状態を観測する。

少なくとも以下を確認する。

### 構造的条件

- 要求が1件以上存在する
- 各要求に識別子が存在する
- 各要求に要求対象が存在する
- 各要求に期待状態が存在する
- 各要求が対象サイクルに紐付いている

### 意味論的条件

当該サイクルで扱う要求が十分に記録されていること。

これは完全には機械的に判定できないため、必要に応じて意味論的判断を利用する。

さらに、要求者による要求合意が必要な場合、その合意状態を観測可能な形で確認する。

---

# 3. 要件定義プロセス

## 3.1 目的

要求を到達させるために、システムが満たさなければならない条件を導出する。

要件は、要求を詳細化したものではない。

要求と要件の違いは抽象度ではなく、観点にある。

```text
要求
= 要求者が期待する状態

要件
= その要求状態へ到達するために、
  システムが満たさなければならない条件
```

---

## 3.2 要件の定義

要件とは、

> **要求状態へ到達するために、システムが満たす必要がある制約または条件**

である。

例えば、要求が、

```text
営業担当は自分の営業情報だけを閲覧でき、
管理者はすべて閲覧でき、
メンターは担当営業の案件情報も閲覧できるようにしてほしい。
```

である場合、以下の要件を導出できる。

```text
- 利用者の役割を識別できること
- 営業情報の担当者を識別できること
- メンターと営業担当の関係を識別できること
- 営業担当には本人の営業情報だけを提供すること
- 管理者にはすべての営業情報を提供すること
- メンターには担当営業の営業情報を提供すること
```

---

## 3.3 要求到達と要件充足

要求は状態変化への期待であるため、要求については「到達」という表現を用いる。

要件はシステムが満たすべき制約であるため、「充足」という表現を用いる。

```text
要求
→ 到達

要件
→ 充足
```

要求到達を直接かつ客観的に判定できる場合は、その状態を直接評価してよい。

一方、抽象度の高い要求など、要求到達を直接判定することが難しい場合は、

> **その要求から導出されたすべての要件が充足されたことをもって、要求到達と判定する**

ことができる。

概念的には、

```text
要求R
↓
├ 要件A
├ 要件B
└ 要件C

A = 充足
B = 充足
C = 充足

↓

要求R = 到達
```

とする。

したがって、

```text
要求到達
=
要求から導出された全要件の充足
```

を、要求到達の代表的な判定方法として利用できる。

---

## 3.4 入力

要求定義プロセスで生成された要求。

---

## 3.5 プロセス実行者の責務

プロセス実行者は、各要求について、

> その要求状態へ到達するために、システム上どの条件が成立しなければならないか

を導出する。

責務は以下とする。

- 要求ごとに必要な要件を導出する
- 要件を一意に識別可能にする
- 要件の導出元となる要求を明示する
- 明示されていないが要求到達に必要な条件を補完する
- 要求そのものを勝手に変更しない

クライアントから明示されていない事項であっても、要求到達に必要な条件は要件として定義してよい。

---

## 3.6 アーティファクト

### 要件

各要件について、少なくとも以下を持つ。

- 要件識別子
- 要件内容
- 導出元となる要求

例えば、

```text
要件-001

内容:
利用者の役割を識別できること

導出元:
要求-003
```

とする。

一つの要求から複数の要件が導出されてよい。

---

### 要求と要件の関係

要求と要件の関係は、必ず1対多とする。

```text
要求A
├─ 要件A-1
├─ 要件A-2
└─ 要件A-3

要求B
├─ 要件B-1
└─ 要件B-2
```

各要件は、必ず一つの要求のみを導出元として持つ。

複数の要求から同一または類似した条件が導出される場合でも、要件を要求間で共有しない。

例えば、

```text
要求A
→ 利用者の役割を識別できること

要求B
→ 利用者の役割を識別できること
```

のように、同一内容の要件が複数生成されることを許容する。

これは重複排除よりも、要求から要件までの追跡可能性とアーティファクト構造の単純性を優先するためである。

後続の外部設計やEngineeringでは、複数の要件が同一の設計・実装によって満たされる場合、それを重複して設計・実装する必要はない。

AIまたはプロセス実行者は、既存の設計・実装が同一条件を満たしていると判断できる場合、それを再利用してよい。

したがって、

```text
要求と要件
= 必ず1対多

要件と外部設計
= 必ずしも1対1ではない

要件と実装
= 必ずしも1対1ではない
```

という関係とする。

---

## 3.7 アーティファクトの制約

要件は、要求到達のためにシステムが満たす条件として記述する。

この工程では、要件を、

- 機能要件
- データ要件
- 画面要件
- 権限要件

などへ無理に分類する必要はない。

例えば、

```text
- 利用者の役割を識別できること
- 営業情報の担当者を識別できること
- 管理者にはすべての営業情報を提供すること
```

のような箇条書きの条件群でよい。

これらを実際の、

- 機能
- データ
- 画面
- API
- 権限
- 外部連携

などへ変換する責務は、後続の外部設計プロセスが持つ。

---

## 3.8 検証方法は要件定義で固定しない

要件定義では、

> 何を満たす必要があるか

を定義する。

その要件を、

> どの方法で充足確認するか

までは必須としない。

検証方法は、実装された成果物および既存の検証手段を踏まえて、QAプロセスで決定する。

これによって、要件定義を特定のテストレベルや検証技術へ依存させない。

---

## 3.9 プロセスゲート

プロセスゲートは、要求と要件の対応関係を観測する。

少なくとも、

```text
すべての要求
-
要件の導出元として参照された要求
=
0
```

であることを確認する。

つまり、すべての要求について少なくとも一度は、

> この要求へ到達するために、システムが何を満たす必要があるか

が検討されていることを保証する。

要件内容そのものが要求到達に十分かどうかは意味論的判断となる。

---

## 3.10 進行条件

要件定義プロセスから外部設計プロセスへ進行するためには、

- すべての要求が要件導出の対象となっている
- 必要な要件が記録されている
- 各要件の導出元が追跡可能である

こと。

---

# 4. 外部設計プロセス

## 4.1 目的

要件として定義された制約を、実際のシステム仕様へ組み込む。

```text
要求
↓
要件
↓
外部設計
```

の関係は、

```text
要求
= 何を期待しているか

要件
= その期待へ到達するために、
  システムが何を満たす必要があるか

外部設計
= その要件を、どのようなシステム仕様によって実現するか
```

とする。

---

## 4.2 入力

要件定義プロセスで生成された要件。

必要に応じて、

- 現行システム
- 現行アーキテクチャ
- 技術的制約
- 既存仕様

も参照する。

---

## 4.3 プロセス実行者の責務

プロセス実行者は、要件を満たすために必要な外部仕様を設計する。

設計対象は要件によって異なる。

例えば、

```text
要件:
利用者の役割を識別できること
```

に対して、

```text
ユーザー情報として役割を保持する
```

というデータ設計を行うことができる。

また、

```text
要件:
営業情報の担当者を識別できること
```

に対して、

```text
営業情報と利用者を関連付ける
```

というデータ設計を行うことができる。

さらに、

```text
要件:
営業担当には本人の営業情報だけを提供すること
```

に対して、

```text
営業情報取得時に、
認証された利用者と営業情報の担当者を比較し、
取得対象を制限する
```

という機能仕様を設計できる。

---

## 4.4 アーティファクト

### 外部設計

要件を実現するために必要なシステム仕様を記録する。

設計対象は固定しない。

必要に応じて、

- 機能
- データ
- 画面
- API
- 権限
- 外部連携
- エラー時の振る舞い
- その他外部から観測可能な仕様

を設計する。

すべての要件に対して、すべての設計分類を作成する必要はない。

要件を実現するために必要な設計だけを行う。

---

## 4.5 アーティファクトの必須要件

各外部設計には少なくとも、

- 設計識別子
- 対象要件
- 設計内容

を持たせる。

必要に応じて、

- 対象機能
- 入力
- 出力
- データ構造
- 画面状態
- 権限制約
- エラー時の振る舞い
- 他設計との関係

を含める。

---

## 4.6 要件と外部設計の関係

要件は外部設計へ制約として組み込まれる。

例えば、

```text
要件:
利用者の役割を識別できること

↓

外部設計:
利用者データに役割を保持する属性を持つ
```

```text
要件:
営業情報の担当者を識別できること

↓

外部設計:
営業情報と利用者を関連付ける
```

```text
要件:
管理者にはすべての営業情報を提供すること

↓

外部設計:
管理者として識別された利用者による
営業情報取得では対象を制限しない
```

という形で、要件をシステム仕様へ変換する。

---

## 4.7 制約

外部設計プロセスでは、要件を勝手に削除または変更しない。

既存アーキテクチャや技術的制約によって要件を実現できない場合は、その問題を明示する。

また、要求・要件の粒度に応じて、外部設計の粒度も変化してよい。

非常に具体的な要求の場合、外部設計が小さな仕様変更だけになることも許容する。

---

## 4.8 プロセスゲート

プロセスゲートは、要件と外部設計の対応関係を観測する。

少なくとも、

```text
すべての要件
-
外部設計から参照された要件
=
0
```

であることを確認する。

つまり、すべての要件が何らかの外部設計へ明示的に組み込まれていることを保証する。

外部設計が要件を適切に実現できるかどうかは意味論的判断となる。

---

## 4.9 進行条件

外部設計プロセスからEngineeringプロセスへ進行するためには、

- すべての要件が外部設計へ組み込まれている
- 各外部設計が対象要件を追跡可能である
- Engineeringを開始するために必要な外部仕様が記録されている

こと。

---

# 5. 要求・要件・外部設計の関係

ここまでの三つのプロセスは、次の関係を持つ。

```text
要求
│
│ 要求者が期待する状態
│
↓
要件
│
│ 要求状態へ到達するために
│ システムが満たすべき制約
│
↓
外部設計
│
│ 要件を実際のシステム仕様として
│ 組み込む
│
↓
Engineering
```

それぞれの概念は抽象度によって区別しない。

観点によって区別する。

```text
要求
= 期待

要件
= 必要条件

外部設計
= 解
```

また、

```text
要件充足
↓
要求到達
```

という関係を持つ。

要求到達を直接客観的に判定できない場合、

> **その要求から導出された全要件が充足されたことを、要求到達の判定根拠とする。**

要件の充足確認方法は要件定義時点では固定せず、後続のQAプロセスで決定する。

これにより、

```text
要求定義
= 何を期待しているか

要件定義
= 何が成立しなければならないか

外部設計
= どういうシステム仕様にするか

QA
= 本当にその条件が成立しているか
```

という責務分離を行う。
