# AI駆動スパイラル開発 — ISO/IEC/IEEE準拠 標準プロセスモデル

## 1. 位置付け

本ドキュメント群は、AI駆動スパイラル開発における**標準プロセスモデル**を、Systems and Software Engineeringの国際標準に基づいて定義する。

基礎とする規格は以下である。

- ISO/IEC/IEEE 15288:2023 — System life cycle processes
- ISO/IEC/IEEE 12207:2026 — Software life cycle processes
- ISO/IEC/IEEE 29148:2018 — Requirements engineering
- ISO/IEC/IEEE 15289:2019 — Content of life-cycle information items
- 必要に応じて ISO/IEC 25010 — Product quality model

これらの規格は、特定の開発方法論や特定のライフサイクルモデルを強制しない。ISO/IEC/IEEE 15288:2023 は、System Life Cycle Processを反復的・並行的・再帰的に適用できることを前提とし、ISO/IEC/IEEE 12207:2026 もSoftware Life Cycle Processを並行・反復・再帰・増分的に適用できることを明示している。

したがって、本方式ではISO由来のEngineering Processを、Spiral DevelopmentのCycle内で反復適用する。

```text
ISO/IEC/IEEE由来
Engineering Process / Information Item

        ＋

AI駆動スパイラル独自
Cycle / Gate / Semantic Completion / Feedback / Spiral orchestration
```

両者を混同しない。

---

## 2. Standard Process

本方式の標準プロセスは次の9段階とする。

```text
1. Stakeholder Needs and Requirements Definition
      ↓
      StRS

2. System Requirements Definition
      ↓
      SyRS

3. System Architecture Definition
      ↓
      System Architecture
      Requirement Allocation

4. Software Requirements Definition
      ↓
      SRS

5. Software Design
      ↓
      Software Design

6. Implementation
      ↓
      Software

7. Verification
      ↓
      Verification Result

8. Validation
      ↓
      Validation Result

9. Feedback
      ↓
      次Cycle判定
```

各Cycleで全文書をゼロから完成させるのではなく、当該Cycleで必要となる差分を既存Artifactへ反映する。

```text
StRS Δ
  ↓
SyRS Δ
  ↓
Architecture / Allocation Δ
  ↓
SRS Δ
  ↓
Software Design Δ
  ↓
Software Δ
  ↓
Verification
  ↓
Validation
  ↓
Feedback
```

## 3. ISOとの対応関係

本標準プロセスは、ISO/IEC/IEEEのProcess名を単純に並べ替えたものではない。

特にSoftware側については、ISO/IEC/IEEE 12207:2026がISO/IEC/IEEE 15288系のTechnical Process構造と整合したProcess Modelを採用していることを踏まえ、**System ElementとしてSoftwareへ割り当てられた責任をSoftware engineeringの対象へ再帰適用する**。

そのため、本方式の `Software Requirements Definition` は、ISO/IEC/IEEE 12207:2026における `System/Software Requirements Definition` のSoftwareへの適用を、責任境界が明確になるように名称化したものである。

同様に `Software Design` は、Software System Elementに対するArchitecture / Design Definitionの責務を、本方式上のSoftware責任としてまとめて表現する。

つまり、

```text
国際標準のProcess framework
≠
本方式の表示上のProcess名を逐語的に規定
```

であり、

```text
国際標準のPurpose / Outcome / Responsibility boundary
→ 本方式の標準プロセスへ対応付ける
```

ことを原則とする。

# 4. Stakeholder Needs and Requirements Definition

## 4.1 目的

Stakeholder Needs and Requirements Definitionは、StakeholderがSystem-of-Interestに対して必要としているCapability、期待、制約、利用状況を明確にし、Stakeholder Needs and Requirementsとして定義する。

ISO/IEC/IEEE 15288:2023のStakeholder Needs and Requirements Definition Processを基礎とする。

このProcessが扱う中心的な問いは、

> **Stakeholderは何を必要としているか**

である。

System内部の構造、Software仕様、実装方法をここで決定しない。

## 4.2 入力

主な入力は以下とする。

- Stakeholderとの会話、ヒアリング、要求
- Business / Mission上の目的
- Operational Concept / 利用状況
- 現行業務、現行Systemの問題
- 法令、契約、外部制約
- 前CycleのValidation Result
- 前Cycleから継続するStakeholder Needs / Requirements

## 4.3 責務

Process実行者は少なくとも以下を行う。

- Stakeholderを識別する
- Stakeholder Needsを抽出する
- Stakeholder Requirementsとして明確化する
- Context of Use / Operational Conceptを必要に応じて記録する
- Constraintを識別する
- Requirements間の矛盾を明らかにする
- 発生源と追跡関係を保持する
- Stakeholderの期待を不必要にSystem内部仕様へ変換しない

## 4.4 Output Artifact — StRS

本方式では、このProcessの主要Information Itemを `StRS` と呼ぶ。

StRSは少なくとも以下を表現する。

- Stakeholder
- Stakeholder Needs
- Stakeholder Requirements
- 利用環境 / Context of Use
- Operational Scenario / Concept
- 外部制約
- Requirement source
- Traceability

ISO/IEC/IEEE 29148:2018のRequirements EngineeringにおけるStakeholder Requirements Specificationの考え方を基礎とする。

## 4.5 Gate

Gateは少なくとも以下を確認する。

- 当該Cycleで扱うStakeholderが識別されている
- 当該Cycleで扱うNeeds / Requirementsが識別可能である
- 発生源が追跡可能である
- System内部の解決方法をStakeholder Needと混同していない
- 必要なConstraintが記録されている
- 次のSystem Requirements Definitionが開始可能である

# 5. System Requirements Definition

## 5.1 目的

System Requirements Definitionは、Stakeholder Needs and Requirementsを、System-of-Interestが満たすべきTechnical Requirementsへ変換する。

ISO/IEC/IEEE 15288:2023のSystem Requirements Definition Processを基礎とする。

中心的な問いは、

> **System全体は何を満たさなければならないか**

である。

StRSがStakeholder viewを表すのに対し、SyRSはSystem engineering viewを表す。

## 5.2 入力

- StRS
- Stakeholder Needs / Requirements
- Operational Concept
- System boundary
- Applicable constraints
- 既存System Requirements
- 前CycleのSyRS

## 5.3 責務

Process実行者は少なくとも以下を行う。

- Stakeholder RequirementsをSystem Requirementsへ変換する
- System boundaryを明確化する
- Systemが提供すべきFunction / Capabilityを定義する
- External Interface Requirementsを定義する
- Performance / Security / Reliability等のQuality Requirementsを定義する
- ConstraintをSystem Requirementとして明確化する
- Verification可能な形へRequirementを整える
- StRSとのTraceabilityを保持する

## 5.4 Output Artifact — SyRS

SyRSはSystem-of-Interest全体に対するRequirementsを記述する。

少なくとも以下を含む。

- System functional requirements
- System quality requirements
- External interface requirements
- System constraints
- Verification criteria / verification consideration
- StRSとのtraceability
- Requirement identifier

SyRSはSoftware Requirementではない。

SystemがHardware、Software、Human、Procedure、External Service等の複数System Elementから構成される場合でも、ここではまだSystem全体の責任として表現する。

## 5.5 Gate

- 当該Cycleで必要なSystem Requirementsが識別されている
- StRSからSyRSへのTraceabilityが存在する
- RequirementがSystem boundaryに対して記述されている
- 必要なQuality / Interface / Constraintが欠落していない
- Verification可能性が考慮されている
- Architecture Definitionへ進むために十分なSystem Requirementが存在する

# 6. System Architecture Definition

## 6.1 目的

System Architecture Definitionは、SyRSを満たすSystem Architectureを定義し、System RequirementsをSystem Elementsへ割り当てる。

ISO/IEC/IEEE 15288:2023のSystem Architecture Definition Processを基礎とする。

中心的な問いは、

> **SystemをどのSystem Elementsで構成し、どのRequirementをどこが担うか**

である。

このProcessによって、System RequirementsとSoftware Requirementsの責任境界が形成される。

## 6.2 入力

- SyRS
- StRS
- System context
- Existing architecture
- Architecture constraints
- Technology / organizational constraints
- 前CycleのSystem Architecture

## 6.3 責務

Process実行者は少なくとも以下を行う。

- System Elementsを識別する
- Element間の責任境界を定義する
- Interfaceを定義する
- System RequirementsをSystem ElementsへAllocationする
- Architecture alternativesを必要に応じて評価する
- Architecture decisionと根拠を追跡可能にする
- Allocation結果をSyRSまで追跡可能にする

## 6.4 Output Artifact — System Architecture / Requirement Allocation

### System Architecture

System Architectureは少なくとも以下を表現する。

- System Elements
- Element responsibility
- Element relationship
- Interface
- Boundary
- Architecture constraints
- Architecture decisions

### Requirement Allocation

Requirement Allocationは、System RequirementをどのSystem Elementが担うかを記録する。

```text
SyRS Requirement
  ↓ allocation
System Element
```

Softwareへ割り当てられたRequirementのみが、後続のSoftware Requirements Definitionの直接入力となる。

## 6.5 Gate

- System ArchitectureがSyRSを説明できる
- 必要なSystem Elementsが識別されている
- Element間のInterface / Boundaryが明確である
- 当該CycleのSystem RequirementsにAllocation先が存在する
- Softwareへ割り当てられた責任が識別できる
- SyRS → Architecture → AllocationのTraceabilityが存在する
- Software Requirements Definitionを開始できる

---

## 7. Traceability

この段階までのTraceabilityは最低限以下を保持する。

```text
Stakeholder Need / Requirement
        ↓
       StRS
        ↓
System Requirement
        ↓
       SyRS
        ↓
System Architecture
        ↓
Requirement Allocation
        ↓
System Element
```

次文書では、SoftwareへAllocationされた責任をSRS、Software Design、Softwareへ変換するProcessを定義する。
