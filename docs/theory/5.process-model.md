# AI駆動スパイラル開発 — QA / 検収 / フィードバックとStandard Process

本ドキュメントは、QA、検収、フィードバック、およびAI駆動スパイラル開発におけるStandard Process全体を定義する。

本方式では、AI駆動スパイラルのProcess粒度とISO/IEC/IEEEのProcess粒度を1:1対応させない。

AI駆動スパイラルのProcessは概念的に次の単位である。

```text
Process
├─ Executor
├─ Artifact(s)
└─ Gate
```

したがって1 Artifact = 1 Processとはしない。一つのStandard Processが複数Artifactを生成・更新し、それらを一つのGateでまとめて判定してよい。

ISO/IEC/IEEEへ整合させる対象は、AI駆動スパイラル独自の8工程や順序そのものではなく、各Artifactの意味・構造・性質と、それを導出するEngineering Process / Activityの責任境界である。

---

# 6. QA

## 6.1 位置付け

`QA` は、Integrated Softwareがspecified Software Requirementsへ適合しているかをVerificationとして確認するStandard Processである。

Engineering責任としてISO/IEC/IEEE 12207:2026のVerification Processを基礎とする。

中心的な問いは、

> **指定したSoftware Requirementsどおりに作られているか**

である。

QAというStandard Process名は利用者向けの名称であり、ISO/IEC/IEEEのProcess名をそのまま採用したものではない。

## 6.2 VerificationとImplementation local checks

`実装` Process内部のUnit Test、Type Check、Lint、Static Analysis、Quality Guard等は、Software Element Design / Implementationを成立させるための局所feedbackとして利用できる。

QAでは既存Evidenceを再利用してよいが、目的は異なる。

```text
実装内のlocal checks
→ Software ElementをIntegrationへ渡せる状態にする

QA / Verification
→ specified Software Requirementsへの適合性を評価する
```

## 6.3 Output Artifact — Verification Result

Verification Resultは少なくとも以下を追跡可能にする。

- Software Requirement identifier
- Verification target
- Verification method
- Evidence
- Result
- failure cause
- unresolved items
- 必要に応じたQuality references

Verification Resultは単なるTest Result一覧ではなく、Requirementに対する適合性を説明できる必要がある。

## 6.4 Gate

QA Gateは少なくとも以下を確認する。

- 当該Cycleの対象Software Requirementsが識別されている
- Integrated SoftwareがVerification targetとして識別できる
- 各対象Software RequirementにVerification Resultが存在する
- Verification method / Evidence / Resultが記録されている
- specified Software Requirementsへの不適合が次工程へ進めない状態で残っていない
- 検収へ渡せる状態である

Verification上の不適合は原因に応じて適切な上位Processへのfeedback対象となる。この戻り先判断はAI駆動スパイラル独自のorchestrationである。

# 7. 検収

## 7.1 位置付け

`検収` は、成果がStakeholder Needs / Requirementsおよびintended useを満たしているかをValidationとして確認するStandard Processである。

Engineering責任としてISO/IEC/IEEE 12207:2026のValidation Processを基礎とする。

中心的な問いは、

> **Stakeholderが必要としていた成果になっているか**

である。

QAがspecified Software Requirementsへの適合を見るのに対し、検収はStakeholder Needs / intended useへの適合を見る。

```text
QA / Verification
Software Requirements → Integrated Software
「仕様どおりか」

検収 / Validation
Stakeholder Needs / Intended Use → 成果
「必要としていたものか」
```

## 7.2 Output Artifact — Validation Result

Validation Resultは少なくとも以下を追跡可能にする。

- Stakeholder Requirement identifier
- intended use / scenario
- Validation method
- Evidence
- Result
- Stakeholder feedback
- 関連するSystem / Software Requirements
- 関連するVerification Result
- feedback candidate

Verificationがpassしていても、RequirementsそのものがStakeholder Needを十分に表現していなければValidationはfailし得る。

## 7.3 Gate

検収 Gateは少なくとも以下を確認する。

- 当該Cycleで対象となるStakeholder Needs / RequirementsがValidationされている
- intended use / scenarioが考慮されている
- Validation ResultにEvidenceとResultが存在する
- 必要なtraceabilityが存在する
- Validation failの場合にfeedback candidateが明示されている
- フィードバック工程へ判断材料を渡せる状態である

Validationがfailしても、構造的に必要なfeedback candidateが明示されていれば、同一Cycleを無限に完了不能とする必要はない。

# 8. フィードバック

## 8.1 位置付け

`フィードバック` はISO/IEC/IEEE由来のEngineering Processではなく、AI駆動スパイラル開発がCycleを反復するための独自Standard Processである。

中心的な問いは、

> **このCycleの結果を受けて、次Cycleが必要か**

である。

## 8.2 入力

- Validation Result
- Verification Result
- unresolved items
- Stakeholder feedback
- 新規Need / Requirement
- Risk / quality / schedule等の判断材料
- 当該Cycleで得られた学習

## 8.3 Output — Next-cycle decision

```text
needNextCycle = false
→ 現時点のSpiralを終了可能

needNextCycle = true
→ 次Cycleを生成
```

Feedback、Cycle、Gateによる反復制御はAI駆動スパイラル独自のorchestrationであり、ISO/IEC/IEEEがこのMechanismを規定しているという意味ではない。

---

# 9. Standard Process 最終構成

AI駆動スパイラルのStandard Processは次の8工程とする。

```text
1. 要求定義
   → StRS

2. システム要件定義
   → SyRS
   → System Architecture Description

3. ソフトウェア要件定義
   → SRS
   → Software Architecture Description

4. 実装
   → Software Element Design
   → Implemented Software Element
      ↺ Software Element単位でDesign / Implementation

5. 統合
   → Integrated Software

6. QA
   → Verification Result

7. 検収
   → Validation Result

8. フィードバック
   → Next-cycle decision
      ↺
```

Process名は利用者・実行者が理解しやすい日本語名を採用する。ISO由来Process名をStandard Process名としてそのままコピーすることを目的としない。

# 11. 各ProcessのGate責任

## 11.1 要求定義 Gate

StRSについて、当該Cycleで必要なStakeholder Requirements情報が定義・判断済みであることを確認する。

## 11.2 システム要件定義 Gate

SyRSとSystem Architecture Descriptionを一体として確認し、当該CycleのSystem RequirementsとSystem構造・責任割当が次のSoftware Requirements導出に利用可能な状態であることを確認する。

## 11.3 ソフトウェア要件定義 Gate

SRSとSoftware Architecture Descriptionを一体として確認し、Software Requirements、Software Elements、architecture-level relationship / interface、Software Requirement → Software Elementのtraceabilityが実装Processへ渡せる状態であることを確認する。

## 11.4 実装 Gate

当該Cycleで対象となる全Software Elementsについて、Software Element DesignとImplemented Software Elementが対応し、必要なlocal test / static analysis / Quality Guardを通過し、Integrationへ渡せる状態であることを確認する。

SRS適合性の最終判定はここで行わずQAへ残す。

## 11.5 統合 Gate

対象Implemented Software ElementsがArchitecture / Design上のrelationship / interfaceに従って統合され、QAへ渡せるIntegrated Softwareになっていることを確認する。

## 11.6 QA Gate

Integrated Softwareがspecified Software Requirementsへ適合しているかをVerification Resultとして確認する。

## 11.7 検収 Gate

成果がStakeholder Needs / intended useを満たすかをValidation Resultとして確認する。

## 11.8 フィードバック

ValidationおよびCycleで得られた学習から次Cycleの必要性を判断する。

GateはAI駆動スパイラル独自の完了判定であり、ISO/IEC/IEEEがこれらのGateを要求しているという意味ではない。

# 12. Software Element単位の実装orchestration

`実装` Processでは、Software Architecture Descriptionで識別されたSoftware Elementsを実行単位とする。

```text
Software Architecture Description
        ↓
Software Elements / dependency graph
        ↓
ready Software Elements
        ↓
Design Definition
        ↓
Software Element Design
        ↓
Implementation
        ↓
Implemented Software Element
        ↓
Local Test / Static Analysis / Quality Guard
        ↺ 必要ならDesign Definitionへ戻る
```

Software Architecture Descriptionのdependency / relationship graphに基づいて実行順序を決定し、dependencyのないSoftware Elementsは並列実行可能とする。

全対象Software ElementsのDesign / Implementationが完了した時点で一つの`実装` Gateを成立させ、その後`統合`へ進む。

この具体的なElement単位のScheduling、並列化、Gate、Quality Guard feedback loopはAI駆動スパイラル独自のorchestrationであり、ISO/IEC/IEEEがこのAlgorithmを要求しているという意味ではない。

# 13. End-to-End Traceability

Standard Processでは最低限、以下のTraceabilityを維持する。

```text
Stakeholder Need / Requirement
        ↓
       StRS
        ↓
System Requirement
        ↓
       SyRS
        ↓
System Architecture Description
        ↓ allocation / traceability
System Element / Software responsibility
        ↓
Software Requirement
        ↓
       SRS
        ↓
Software Architecture Description
        ↓ allocation / traceability
Software Element
        ↓
Software Element Design
        ↓
Implemented Software Element
        ↓
Integrated Software
        ↓
Verification Result
        ↓
Validation Result
        ↓
Next-cycle decision
```

Requirement Allocationを独立したStandard Processまたは独立したStandard Artifactとして挟まない。

System Requirements → System Elementsのallocation / traceabilityはSystem Architecture Descriptionが保持する。

Software Requirements → Software Elementsのallocation / traceabilityはSoftware Architecture Descriptionが保持する。

Verificationはspecified Software Requirementsへ戻るTraceabilityを、ValidationはStakeholder Needs / intended useへ戻るTraceabilityを主に利用する。

# 14. CoreとStandard Processの責任分離

Core Frameworkは具体的なProcess種類を知らない。

```text
Cycle
Process
Executor
Artifact
ArtifactRepository
Gate
Semantic Completion
Feedback contract
Spiral
```

Standard Processは、そのCore上で利用者向けにEngineering責任を束ねる。

```text
要求定義
→ システム要件定義
→ ソフトウェア要件定義
→ 実装
→ 統合
→ QA
→ 検収
→ フィードバック
```

この8工程はAI駆動スパイラル独自のProcess Modelであり、ISO/IEC/IEEEがこの工程分割や順序をLifecycle Modelとして要求しているという意味ではない。

# 15. Spiralとしての反復適用

```text
Cycle N
要求定義 Δ
→ システム要件定義 Δ
→ ソフトウェア要件定義 Δ
→ 実装 Δ
→ 統合 Δ
→ QA
→ 検収
→ フィードバック

             ↓ needNextCycle

Cycle N+1
要求定義 Δ
→ ...
```

各Cycleで全文書をゼロから作り直すのではない。Artifactは継続的に存在し、各Cycleで必要な差分を反映する。
