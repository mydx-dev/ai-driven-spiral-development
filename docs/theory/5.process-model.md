# AI駆動スパイラル開発 — 下流プロセスモデル

# 6. QAプロセス

## 6.1 目的

QAプロセスは、Engineeringプロセスによって生成された実装成果物について、各要件が実際に充足されていることを検証する。

Engineeringプロセスが、

> **外部設計を正しく実装すること**

を主な責務とするのに対し、QAプロセスは、

> **実装されたシステムによって要件が実際に充足されていることを確認すること**

を責務とする。

```text
要求
↓
要件
↓
外部設計
↓
Engineering
↓
実装成果物
↓
QA
↓
要件充足結果
```

---

## 6.2 入力

QAプロセスは、少なくとも以下を入力として利用する。

- 要求
- 要件
- 外部設計
- 実装成果物
- Engineeringプロセスで生成されたテストおよびその結果
- 静的解析結果
- Build結果
- Review結果
- その他、要件充足を判断するために利用可能な情報

QAはEngineeringプロセスの検証を最初からやり直すことを目的としない。

既存の検証結果によって要件充足を十分に確認できる場合、その結果を証拠として利用する。

---

## 6.3 プロセス実行者の責務

QA実行者は、各要件について、

> **現在の実装成果物によって、この要件が実際に充足されているか**

を判定する。

主な責務は以下とする。

- すべての要件を検証対象とする
- 各要件について充足状態を判定する
- 要件充足の根拠を記録する
- 既存の検証結果が利用可能か確認する
- 既存の検証だけでは不足する場合、追加検証を行う
- 必要に応じてテストを追加する
- 必要に応じてE2E等の横断的な検証を行う
- ソースコード、設定、Schema、Migration等を直接確認する
- システム外部の設定について、必要に応じて人間による検証を要求する
- 要件が充足されていない場合、その事実を記録する

QA実行者自身が、要件を満たすために実装成果物を修正することは原則として責務としない。

修正が必要な場合は、Engineering側の実装成果物を再度更新する。

---

## 6.4 検証方法

要件の検証方法は固定しない。

要件の性質に応じて、その要件が充足されていることを最も適切に確認できる方法を選択する。

例えば、

```text
要件:
利用者の役割を識別できること

検証例:
- Schemaを確認する
- Migrationを確認する
- 実際のDatabase構造を確認する
```

```text
要件:
営業担当には本人の営業情報だけを提供すること

検証例:
- 既存の結合テストを確認する
- APIのテスト結果を確認する
- 不足している場合は追加テストを作成する
```

```text
要件:
一連の業務操作によって営業情報を共有できること

検証例:
- 既存テストだけでは確認できない
- E2Eによってユーザーシナリオを検証する
```

したがって、

> **QAはテストを作るプロセスではなく、要件充足を検証するプロセスである。**

テストは、そのために利用可能な検証手段の一つにすぎない。

---

## 6.5 非機能要件の検証

非機能的な要件についても、他の要件と同様に充足状態を検証する。

例えば、

- Performance
- Security
- Availability
- Backup
- Infrastructure
- External Service Configuration

など、ソースコードだけでは確認できない要件が存在し得る。

その場合、QA実行者が単独で検証可能であることを要求しない。

必要に応じて人間や外部の検証主体による確認を行い、その結果をQAアーティファクトへ記録する。

---

## 6.6 アーティファクト

### QA結果

各要件について、少なくとも以下を記録する。

- 要件識別子
- 充足状態
- 検証根拠
- 必要に応じて検証方法
- 必要に応じて補足事項

例えば、

```text
要件-001
状態: 充足

根拠:
Database SchemaおよびMigrationによって
利用者の役割を保持する構造が実装されていることを確認。
```

```text
要件-002
状態: 充足

根拠:
既存のIntegration Testによって、
営業担当者による取得対象の制限を確認。
```

---

## 6.7 要求到達との関係

要求到達を要件充足によって判定する要求については、その要求から導出されたすべての要件が充足された場合、要求到達として扱うことができる。

```text
要求R
│
├ 要件A → 充足
├ 要件B → 充足
└ 要件C → 充足
       │
       ↓
   要求R → 到達
```

ただし、この要求到達は開発側による判定である。

要求者自身による最終的な評価は、後続の検収プロセスで行う。

---

## 6.8 プロセスゲート

QAプロセスゲートはQA結果を観測する。

進行条件は、

- すべての要件について検証が実施されている
- すべての要件が充足状態である
- 各充足判定に根拠が存在する
- 必要な非機能要件の検証が完了している
- 未解決のQA不備が存在しない

こと。

要件が一つでも未充足である場合、リリースプロセスへ進行しない。

必要な修正をEngineering側へ戻し、修正後に再度QAを行う。

```text
QA
│
├─ 要件未充足
│      ↓
│  Engineering
│      ↓
│     QA
│
└─ 全要件充足
       ↓
   リリース
```

---

# 7. リリースプロセス

## 7.1 目的

リリースプロセスは、QAを通過した実装成果物を、要求者が検収可能な一意の成果物として固定し、引き渡し可能な状態にする。

```text
QA済み実装成果物
↓
リリース
↓
検収可能な成果物
```

リリースプロセスは、新たな要求や要件を実現する工程ではない。

既に検証された実装成果物を、

> **何を、どの状態で、どのように要求者へ引き渡すのか**

が明確な状態にする。

---

## 7.2 入力

少なくとも以下を入力とする。

- QAを通過した実装成果物
- QA結果
- 要求
- 要件
- 外部設計
- リリースに必要な環境情報
- 既存のリリース方式

---

## 7.3 プロセス実行者の責務

リリース実行者は、QA済みの実装成果物を検収可能な状態へ変換する。

主な責務は以下とする。

- リリース対象を一意に特定する
- 必要に応じてVersionを付与する
- 必要なDeploymentを実施する
- 必要なMigrationを実施する
- リリース内容を記録する
- リリース手順を記録する
- 要求者による確認方法を納品手順として記録する
- 検収対象となる環境または成果物を明確にする

リリース実行者は、要求・要件・外部設計を変更しない。

---

## 7.4 アーティファクト

### リリースアーティファクト

リリースアーティファクトは、検収対象として固定された成果物およびその付随情報の集合である。

必要に応じて以下を含む。

- リリース対象
- Version
- リリースノート
- リリース手順書
- 納品手順書
- Deployment情報
- Migration情報
- 検収対象環境
- その他、成果物を特定・利用するために必要な情報

---

## 7.5 リリース手順書

リリース手順書は、

> **成果物をどのようにリリース可能な状態へ反映するか**

を記録する。

例えば、

```text
Build
↓
Migration
↓
Deploy
↓
Configuration
↓
Smoke Check
```

など。

具体的な内容は技術スタックおよびリリース方式に依存する。

---

## 7.6 納品手順書

納品手順書は、

> **要求者が、リリースされた成果物をどのように知覚・操作し、要求状態への到達を評価すればよいか**

を記録する。

原則として要求を起点に構成する。

例えば、

```text
要求-001

期待状態:
顧客一覧から過去の商談履歴を確認できる

確認手順:
1. 指定された環境へアクセスする
2. 指定された利用者としてログインする
3. 顧客一覧を開く
4. 対象顧客を確認する
5. 過去の商談履歴が表示されることを確認する
```

納品手順書はQA手順書ではない。

QAが要件充足を技術的に検証するのに対して、納品手順書は要求者が成果物を知覚し、自身の期待した状態に到達しているかを評価するために使用する。

---

## 7.7 納品の位置付け

納品は独立したプロセスとはしない。

納品とは、

> **リリースアーティファクトを要求者へ引き渡し、検収を開始可能にする行為**

である。

```text
リリースプロセス
↓
リリースアーティファクト
↓
納品
↓
検収プロセス
```

したがって、納品はリリースプロセスと検収プロセスの境界で発生する受け渡し活動として扱う。

---

## 7.8 プロセスゲート

リリースプロセスゲートは、リリースアーティファクトを観測する。

少なくとも、

- リリース対象が一意に特定できる
- QAを通過した実装成果物と一致している
- 必要なリリース処理が完了している
- 必要なMigration等が完了している
- リリースノートが存在する
- 必要なリリース手順が記録されている
- 納品手順が存在する
- 要求者が検収可能な状態である

ことを確認する。

すべてを満たした場合、リリースアーティファクトを要求者へ納品し、検収プロセス実行者を起動する。

---

# 8. 検収プロセス

## 8.1 目的

検収プロセスは、要求者が実際の成果物を知覚・操作し、自身が期待した要求状態へ到達しているかを評価する。

```text
要求
↓
開発
↓
リリース成果物
↓
要求者による知覚
↓
要求状態の評価
```

検収は、単にQA結果を再確認するプロセスではない。

QAが、

> **システムが要件を充足しているか**

を評価するのに対し、検収では、

> **その結果として、要求者が期待した状態へ本当に到達したか**

を評価する。

---

## 8.2 入力

少なくとも以下を入力とする。

- 要求
- リリースアーティファクト
- 納品手順書
- QA結果

必要に応じて要件や外部設計も参照してよい。

---

## 8.3 プロセス実行者の責務

検収実行者は、要求を起点としてリリース成果物を評価する。

主な責務は以下とする。

- 各要求について成果物を確認する
- 納品手順に従って成果物を操作する
- 期待状態へ到達しているか評価する
- 要求到達結果を記録する
- 成果物を知覚したことで発生した新しい要求を記録する
- 既存要求の変更を記録する
- 不要となった要求を記録する

検収実行者は、必ずしも技術的な詳細を理解する必要はない。

検収の中心は、要求者自身による成果物の知覚と評価である。

---

## 8.4 QAと検収の違い

QAと検収では評価対象が異なる。

```text
QA
│
├ 対象: 要件
├ 判定: 充足 / 未充足
└ 主体: 開発側
```

```text
検収
│
├ 対象: 要求
├ 判定: 到達 / 未到達
└ 主体: 要求者
```

例えば、

```text
要求:
営業情報の共有を効率化したい
```

に対して、QAでは、

```text
要件A → 充足
要件B → 充足
要件C → 充足
```

を確認し、開発側として要求到達と判断できる。

しかし実際の成果物を要求者が利用した結果、

```text
「情報は共有できるが、
毎回検索する必要があるので思ったより面倒だった」
```

という評価が生じることがある。

これはQAの失敗とは限らない。

成果物を知覚したことで要求者自身の要求に対する解像度が上がった結果として扱う。

---

## 8.5 要求未到達と新しい要求の区別

検収では、少なくとも以下を区別する。

### 要求未到達

合意された要求状態に成果物が到達していない。

```text
期待:
商談履歴が表示される

実際:
商談履歴が表示されない
```

これは現在のサイクルに対する不備である。

必要な修正を行う。

### 新規要求

既存要求には到達しているが、成果物を知覚したことで新しい期待が発生した。

```text
既存要求:
商談履歴を表示してほしい

結果:
表示されている

新しい期待:
商談履歴を日付で絞り込みたい
```

これは現在サイクルの失敗とはしない。

次サイクルの要求候補とする。

### 要求変更

成果物を知覚した結果、既存の要求状態そのものを変更したくなった。

```text
旧要求:
一覧画面に商談履歴を表示したい

新しい期待:
一覧ではなく詳細画面に表示したい
```

変更後の要求を次サイクルの入力候補とする。

### 要求取消

成果物を知覚した結果、その要求自体が不要であることが判明した。

これも要求理解が進んだ結果として記録する。

---

## 8.6 アーティファクト

### 検収結果

各要求について、少なくとも以下を記録する。

- 要求識別子
- 要求到達状態
- 要求者による評価
- 必要に応じて補足

さらに、検収によって発見された、

- 新規要求
- 変更要求
- 取消要求
- 現サイクルの不備

を記録する。

---

## 8.7 フィードバックの位置付け

フィードバックは独立したプロセスとはしない。

フィードバックは、

> **要求者が成果物を知覚・評価した結果として生成される検収アーティファクトの一部**

として扱う。

```text
検収
↓
検収結果
├ 要求到達結果
├ 新規要求
├ 変更要求
├ 取消要求
└ 現サイクルの不備
```

したがって、フィードバックを収集するためだけの独立したプロセス実行者およびプロセスゲートは設けない。

---

## 8.8 プロセスゲート

検収プロセスゲートは検収結果を観測する。

すべての要求について評価が完了した場合、フィードバックを確認する。

```text
検収完了
      │
      ├─ 新規・変更要求なし
      │        ↓
      │    Spiral終了
      │
      └─ 新規・変更要求あり
               ↓
          Cycle N+1
               ↓
          要求定義実行者
```

要求取消のみの場合は、残存する新規・変更要求の有無によって次サイクルの必要性を判定する。

---

# 9. 下流プロセス全体

下流工程は、以下の3つのプロセスによって構成する。

```text
Engineering
     │
     ↓
┌──────────── QA ────────────┐
│                            │
│ QA実行者                   │
│     ↓                      │
│ QA結果                     │
│     ↑                      │
│ QAゲート                   │
└─────┬──────────────────────┘
      │ 全要件充足
      ↓
┌──────── リリース ──────────┐
│                            │
│ リリース実行者             │
│     ↓                      │
│ リリースアーティファクト    │
│     ↑                      │
│ リリースゲート             │
└─────┬──────────────────────┘
      │
      │ 納品
      ↓
┌────────── 検収 ────────────┐
│                            │
│ 検収実行者                 │
│     ↓                      │
│ 検収結果                   │
│     ↑                      │
│ 検収ゲート                 │
└─────┬──────────────────────┘
      │
      ├─ 不備あり → Engineering / QAへ戻る
      │
      ├─ 新規・変更要求あり → 次Cycle
      │
      └─ 新規・変更要求なし → Spiral終了
```

この構造によって、

```text
Engineering
= 外部設計を実装する

QA
= 要件充足を確認する

リリース
= 検収可能な成果物として固定する

納品
= 成果物を要求者へ引き渡す

検収
= 要求者が要求到達を評価する

フィードバック
= 検収によって得られた次の要求
```

という責務分離を行う。

最終的に、

```text
要求
↓
要件
↓
外部設計
↓
Engineering
↓
QA
↓
リリース
↓
検収
      │
      └──────────→ 次Cycleの要求
```

という閉じたフィードバックループを形成する。

このループを反復することによって、成果物に対する要求者の知覚を継続的に次の開発へ反映する。
