# AI駆動スパイラル開発 — Verification / Validation / Feedback

本ドキュメントは、Implementation後のVerification、Validation、およびAI駆動スパイラル独自のFeedbackを定義する。

VerificationとValidationはISO/IEC/IEEE由来のEngineering Processである。

FeedbackはISO/IEC/IEEEのEngineering Process名ではなく、AI駆動スパイラル開発がCycleを反復するために定義するLifecycle orchestration上の責務である。

```text
ISO由来
Verification
Validation

AI駆動スパイラル独自
Feedback
```

両者を明確に分離する。

---

# 7. Verification

## 7.1 目的

Verificationは、System / Softwareが**specified requirementsを満たしていること**を客観的Evidenceによって確認する。

ISO/IEC/IEEE 15288:2023およびISO/IEC/IEEE 12207:2026のVerification Processを基礎とする。

中心的な問いは、

> **指定したRequirementsどおりに作られているか**

である。

本方式では主として、SyRSおよびSRSに対する適合性をVerification対象とする。

## 7.2 VerificationとImplementation内Testの違い

Implementation内のTestは、Softwareを構築する活動の一部として実施できる。

Verificationでは、その既存Evidenceを再利用してよいが、目的は異なる。

```text
Implementation Test
→ 実装責務が正しく実現されているか

Verification
→ specified requirementsが満たされていることを確認できるか
```

Verificationは必ずしも新しいTestを作るProcessではない。

既存Test、Inspection、Analysis、Static Analysis、Review、Demonstration、Measurement等をEvidenceとして利用してよい。

## 7.3 入力

- SyRS
- SRS
- System Architecture / Requirement Allocation
- Software Design
- Software
- Implementation時のTest Result
- Static Analysis / Build Result
- その他Verification Evidence

## 7.4 責務

Process実行者は少なくとも以下を行う。

- Verification対象Requirementを識別する
- RequirementごとのVerification methodを決定・確認する
- 利用可能なEvidenceを収集する
- 不足する場合に追加Verificationを実施する
- Requirementごとに適合 / 不適合を判定する
- Evidenceと判定結果を記録する
- 不適合を追跡可能にする

## 7.5 Output Artifact — Verification Result

Verification Resultは少なくとも以下を持つ。

- Requirement identifier
- Verification target
- Verification method
- Evidence
- Result
- Date / revision / tested version等の識別情報
- 不適合がある場合の記録

Verification Resultは、単なるTest Result一覧ではなく、Requirementに対する適合性を説明できることを要求する。

## 7.6 ISO/IEC 25010との関係

ISO/IEC 25010のProduct Quality Modelは、必要に応じてQuality Requirementの定義・分類・評価観点として利用できる。

ただし、Verificationそのものを25010と同一視しない。

例えば、Performance Efficiency、Security、Reliability等をSRS / SyRSのRequirementとして定義した場合、そのRequirementへの適合をVerificationで確認する。

## 7.7 Gate

- 当該CycleでVerification対象となるRequirementsが識別されている
- 各対象RequirementにVerification Evidenceがある
- 各対象Requirementに判定結果がある
- 未解決の重大なRequirement不適合がない
- Validationに進めるSystem / Software状態である

Requirement不適合が存在する場合、必要な上位Processへ戻る。

不具合原因によって戻り先は異なる。

```text
Implementation error → Implementation
Design error         → Software Design
Software Requirement error → Software Requirements Definition
Allocation / System issue   → System Architecture / System Requirements Definition
```

# 8. Validation

## 8.1 目的

Validationは、Systemが**intended use / Stakeholder Needs and Requirementsを満たしていること**を確認する。

ISO/IEC/IEEE 15288:2023およびISO/IEC/IEEE 12207:2026のValidation Processを基礎とする。

中心的な問いは、

> **Stakeholderが必要としていたSystemになっているか**

である。

Verificationがspecified requirementsとの適合を見るのに対し、Validationは現実の利用目的・利用環境・Stakeholder expectationとの適合を見る。

```text
Verification
Requirements → System / Software
「仕様どおりか」

Validation
Stakeholder Needs / Intended Use → System
「必要としていたものか」
```

## 8.2 入力

- StRS
- Stakeholder Needs / Requirements
- Context of Use / Operational Concept
- Verified System / Software
- Verification Result
- Validation scenario / acceptance context
- 前CycleのValidation Result

## 8.3 責務

Process実行者は少なくとも以下を行う。

- Validation対象となるStakeholder Needs / Requirementsを識別する
- Intended Use / Context of Useを考慮する
- Stakeholder視点でSystemを評価する
- 必要なScenario / Demonstration / Operational evaluation等を実施する
- Stakeholder Need / Requirementごとに結果を記録する
- Verification済みでもStakeholder Needを満たさないGapを識別する

Validationは「Requirementが全部passしたから自動的にpass」とは限らない。

RequirementそのものがStakeholder Needを十分に表現していなければ、VerificationがpassしてもValidationがfailすることがある。

この差がVerificationとValidationを分離する最大の理由である。

## 8.4 Output Artifact — Validation Result

Validation Resultは少なくとも以下を持つ。

- Stakeholder Need / Requirement identifier
- Intended use / validation context
- Validation method / scenario
- Evidence
- Result
- Gap / issue
- Stakeholder observationまたはそれに相当する評価

## 8.5 Gate

- 当該Cycleで対象となるStakeholder Needs / RequirementsがValidationされている
- Intended Use / Context of Useが考慮されている
- Validation ResultにEvidenceがある
- Gap / issueが明示されている
- Cycle Feedbackを行うために十分な情報が存在する

Validationがfailしても、本方式では必ずしもその場で無限に同一Cycleへ留まり続ける必要はない。

結果をFeedbackへ渡し、次Cycleで修正する判断を行える。

# 9. Feedback

## 9.1 位置付け

Feedbackは、ISO/IEC/IEEE由来のTechnical / Engineering Processではない。

AI駆動スパイラル開発がCycleを反復するために定義するLifecycle orchestration上のProcessである。

中心的な問いは、

> **このCycleの結果を受けて、次Cycleが必要か**

である。

## 9.2 入力

- Validation Result
- Verification Result
- 未解決Issue
- Stakeholder feedback
- 新規Need / Requirement
- Risk / quality / schedule等の判断材料
- 当該CycleのArtifact差分

## 9.3 責務

Feedbackは少なくとも以下を判断する。

- Stakeholder Needが十分に満たされたか
- Validation Gapが残っているか
- Verification不適合が残っているか
- 新規Requirement / Constraintが発生したか
- System / Softwareの変更がさらに必要か
- 次Cycleを開始すべきか

## 9.4 Output — 次Cycle判定

FeedbackのOutputは、次Cycleの必要性を示すLifecycle Decisionである。

```text
needNextCycle = false
→ 現時点のSpiralを終了可能

needNextCycle = true
→ 次Cycleを生成
```

次Cycleが必要な場合、Validation ResultやFeedback内容は次CycleのStakeholder Needs and Requirements Definition等の入力となる。

## 9.5 Gate

Feedbackに対して、ISO由来のRequirement completion Gateを適用しない。

Feedbackの完了条件は、少なくとも次Cycleの必要性が判断されていることである。

# 10. Standard ProcessとCoreの責任分離

本標準プロセスは、Core Frameworkとは独立する。

## Core

Coreが定義するのはProcessの種類ではなく、Processを進行させる制御構造である。

```text
Cycle
Process
Artifact
ArtifactRepository
Gate
Semantic Completion
Feedback contract
Spiral
```

CoreはStRS、SyRS、SRS、Verification等の具体的意味を知らない。

## Standard Process

Standard ProcessはSystems / Software Engineering上の具体的責任を定義する。

```text
Stakeholder Needs and Requirements Definition
System Requirements Definition
System Architecture Definition
Software Requirements Definition
Software Design
Implementation
Verification
Validation
Feedback
```

この分離により、Core algorithmを変更せずにStandard Processを国際標準へ追従させられる。

# 11. Spiralとしての反復適用

ISO/IEC/IEEE 15288:2023および12207:2026は、Processを特定の一方向Waterfallとして固定しない。

本方式ではその性質を利用し、Cycle単位で必要なProcessを反復適用する。

```text
Cycle N
StRS Δ
→ SyRS Δ
→ Architecture / Allocation Δ
→ SRS Δ
→ Design Δ
→ Software Δ
→ Verification
→ Validation
→ Feedback

             ↓ needNextCycle

Cycle N+1
StRS Δ
→ ...
```

重要なのは、各Cycleで全文書を再作成することではない。

Artifactは継続的に存在し、各Cycleで必要な差分を反映する。

この差分反映とCycle orchestrationがAI駆動スパイラル開発固有の適用方法であり、ISO由来Processそのものと区別する。

# 12. End-to-End Traceability

標準プロセスでは最低限、以下のTraceabilityを維持する。

```text
Stakeholder Need / Requirement
        ↓
       StRS
        ↓
System Requirement
        ↓
       SyRS
        ↓
System Architecture
        ↓
Requirement Allocation
        ↓
Software Requirement
        ↓
       SRS
        ↓
Software Design
        ↓
Software
        ↓
Verification Result
        ↓
Validation Result
        ↓
Feedback
```

VerificationはRequirementsへ戻るTraceabilityを、ValidationはStakeholder Needs / Intended Useへ戻るTraceabilityを主に利用する。

この二つのTraceabilityを分離することで、

```text
specified requirementsを満たしたか
```

と

```text
Stakeholderが本当に必要としていたものを満たしたか
```

を別々に判断できる。

# 13. 参照規格

本標準プロセスの責任境界は、以下を基礎とする。

- ISO/IEC/IEEE 15288:2023 — Systems and software engineering — System life cycle processes
- ISO/IEC/IEEE 12207:2026 — Systems and software engineering — Software life cycle processes
- ISO/IEC/IEEE 29148:2018 — Systems and software engineering — Life cycle processes — Requirements engineering
- ISO/IEC/IEEE 15289:2019 — Systems and software engineering — Content of life-cycle information items (documentation)
- ISO/IEC 25010 — Systems and software Quality Requirements and Evaluation (SQuaRE) — Product quality model

本方式のStandard Process順序、Cycle、Semantic Completion、Gate、Feedbackによる反復制御はAI駆動スパイラル開発の定義であり、ISO/IEC/IEEEがこの順序のLifecycle Modelを強制しているという意味ではない。
