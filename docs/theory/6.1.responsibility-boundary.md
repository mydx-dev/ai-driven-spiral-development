# 責務境界の品質理論

## 1. 目的

Modularity を成立させるためには、単にコードが複数の関数・メソッド・クラスへ分割されていればよいわけではない。

重要なのは、

> **処理が意味のある責務境界へ所属していること**

である。

AI駆動スパイラル開発では、責務を持たない処理境界を作るための構文上の逃げ道を可能な限り機械的に塞ぐ。

これにより実装主体が、

> この処理は誰の責務か

を判断せざるを得ない状態を作る。

この方針はAIエージェントだけでなく、人間の実装者にも適用する。

---

# 2. 責務境界を分割単位とする

Complexity が高い場合、処理を分割する必要がある。

しかしComplexityは、

> どのように分割すべきか

までは示さない。

したがって、

> **複雑度は分割の必要性を示し、モジュール性は分割方法を制約する。**

という関係で品質要件を組み合わせる。

次のような分割は避ける。

```text
前半
後半
step1
step2
normalize helper
validation helper
```

これは処理量や実行順序を基準とした手続き的な分割であり、責務分割とは限らない。

新しい境界を作る場合、その境界は、

- 独立した意味
- 独立した状態
- 独立した変更理由
- 外部との明確な契約
- フレームワークによって要求された責務

などによって存在理由を説明できなければならない。

---

# 3. 所属理由を持たない処理境界を作らない

新しい関数・メソッド・クラス・モジュール等を作る場合、

> **その処理がなぜその型・モジュール・責務に所属するのか説明できなければならない。**

これは意味上の設計原則である。

例えば、

```ts
class GitHubIssue {
  parseBody() {}
}
```

という構造において重要なのは、`class` を利用していることではない。

```text
GitHub Issue の構造を解釈する
↓
GitHubIssue という責務へ所属する
```

という関係が説明できることである。

反対に、

```ts
class GitHubIssue {
  static trimText() {}
  static splitLines() {}
  static normalizeString() {}
}
```

のように、単なる処理置き場として型を利用している場合、責務境界として十分とは限らない。

---

# 4. 問題の本質は構文ではない

責務を持たない処理境界は、様々な構文へ移動できる。

```text
private method
↓
public method
↓
static method
↓
top-level function
↓
local function
```

個別の構文だけを見ると異なる問題に見える。

しかし共通する問題は、

> **責務を持たない処理境界が存在していること**

である。

したがって、

- private
- protected
- public
- static
- helper
- utility
- free function
- local function

といった名称や構文そのものを品質問題の本質とは扱わない。

それぞれを不適切な責務境界を観測するセンサーとして扱う。

---

# 5. private / protected method

例えば、

```ts
class OrderService {
  execute() {}

  private validate() {}
  private normalize() {}
  private prepare() {}
  private calculate() {}
}
```

という構造では、公開APIは小さく見える。

しかし内部で手続き的な処理分割が大量に生成されている可能性がある。

クラスを責務境界として強く扱う設計では、

```text
private / protected method = 0
```

を品質要件として採用できる。

ただし、privateを禁止するだけでは不十分である。

---

# 6. internal-only public method

private禁止だけを導入すると、

```text
private method 禁止
↓
publicへ変更
↓
Lint通過
```

という逃避が成立する。

そのため、

```text
public method
AND
宣言class外からのreference = 0
```

を検出する。

```text
internal-only public method = 0
```

とする。

独立した責務でなければ呼び出し元へ戻す。

独立した責務であれば、適切な責務境界へ分離する。

---

# 7. `this` を利用しない instance method

例えば、

```ts
class User {
  normalize(value: string) {
    return value.trim();
  }
}
```

のようにインスタンス状態を利用しないmethodは、その処理と型の所属関係が弱い兆候となる。

```text
instance method
AND
this reference = 0
→ error
```

とできる。

しかし、このルールだけでは、

```text
thisを利用しない
↓
staticへ変更
↓
チェック回避
```

が成立する。

---

# 8. static method

static methodは、

- instance stateを必要としない
- `class-methods-use-this` 等を回避できる
- instance cohesionの測定から外れやすい
- classをnamespaceとして利用できる

ため、責務を持たない処理の退避先になり得る。

例えば、

```ts
class GitHubIssue {
  static parse() {}
  static normalize() {}
  static split() {}
}
```

という構造では、型名が存在するだけで責務が成立しているとは限らない。

クラスを責務境界として採用する領域では、

```text
static method = 0
```

を原則として採用できる。

## 例外

static method が常に不適切という意味ではない。

例えば、

- declaring class 自身を生成・返却する Factory Method
- Named Constructor
- フレームワークから要求される static API

などは正当な場合がある。

ただし、

```text
method name = create
```

のような名称だけで例外判定してはならない。

可能な限り、

```text
return type
↓
declaring classとの構造的関係
```

などによって判定する。

---

# 9. static-only class

すべての振る舞いがstaticであり、instance stateを持たないclassは、utility namespaceとして利用されている可能性がある。

```ts
class Parser {
  static parse() {}
  static normalize() {}
  static tokenize() {}
}
```

クラスを状態と振る舞いの責務境界として利用する設計では、

```text
static-only class = 0
```

を品質要件とできる。

目的はstatic構文そのものの禁止ではない。

> **classを利用して、所属理由を持たない自由関数群を隠蔽することを防ぐ。**

ことが目的である。

---

# 10. top-level free function

クラスを責務境界として採用するレイヤーでは、責務の所属先が曖昧な自由関数を禁止できる。

例えば、

```ts
function calculateOrderTotal(order: Order) {}
```

が存在する場合、

> この処理は誰の責務か

を先に判断する。

Order自身の責務であれば、

```ts
order.total();
```

とする。

独立した責務なら、その責務を表すオブジェクトやモジュールへ分離する。

ただし、

- React component
- custom hook
- framework callback
- 関数そのものを責務境界として採用する設計

では、自由関数を禁止しない。

ルールは設計モデル・レイヤー単位で適用する。

---

# 11. local named function / local arrow helper

static methodを禁止すると、method内部へ処理を退避できる。

```ts
class Order {
  calculate() {
    function normalize() {}

    const calculateTax = () => {};

    // ...
  }
}
```

method内部に存在することによって責務が成立するわけではない。

そのため対象レイヤーでは、

```text
local named function = 0

変数へ格納した local arrow helper = 0
```

を品質要件として採用できる。

ただし、

```ts
items.map((item) => item.price);
```

のような直接callbackとは区別する。

問題となるのは、

```text
名前を与えられ
独立した処理境界として参照される
local helper
```

である。

---

# 12. single-use trivial boundary

次の条件を組み合わせる。

```text
local only
AND
fan-in <= 1
AND
LOC <= N
AND
Complexity <= N
```

この条件を満たす境界は、複雑度を下げるためだけの手続き分割である可能性がある。

ただし、

```text
fan-in = 1
```

だけを禁止理由にしてはならない。

独立した責務は、一箇所からしか利用されていなくても成立し得る。

あくまで複数条件を組み合わせた低凝集の兆候として扱う。

---

# 13. unused abstraction

品質ゲートを通すためだけに新しい境界を作る逃避も防ぐ。

```text
unused class member = 0

unused export = 0

unused file = 0
```

必要性のないclass、method、moduleを残さない。

---

# 14. God Class への逆方向の逃避

処理の分割先を厳しく制限すると、

```text
新しい境界を作れない
↓
既存classへすべて押し込む
```

という逆方向の逃避が成立する。

そのため、

```text
Complexity
+
method count
+
field count
+
LCOM
+
TCC
+
CBO
+
WMC
```

などによってGod Class / God Methodを観測する。

```text
God Class = 0
```

とする。

---

# 15. 複数のセンサーを組み合わせる

単一ルールによって責務の正しさを証明しようとしてはならない。

```text
巨大な処理
↓
Complexity 上限
↓
分割が必要

private helper
→ 禁止

public helper
→ internal-only publicで検出

instance helper
→ this未使用で検出

static helper
→ staticで検出

static-only class
→ 検出

free function
→ 対象レイヤーで検出

local helper
→ 検出

unused abstraction
→ 検出
```

その結果、

```text
単なる手続き断片を
置く場所が減る
↓
意味のある責務境界への
分割を促す
```

状態を作る。

さらに分割後を、

```text
LCOM <= N
TCC >= N
CBO <= N
Circular Dependency = 0
Forbidden Dependency = 0
God Class = 0
```

などで観測する。

---

# 16. 機械ゲートの目的

機械ゲートだけで、

> この責務分割は意味的に正しい

ことを証明することはできない。

目的は意味的設計を機械へ完全委任することではない。

> **責務を持たない不適切な処理境界を成果物として確定させにくくし、実装主体に意味的な責務判断を要求すること**

が目的である。

AIモデルの能力が高ければ、適切な責務を直接発見できる可能性が高い。

能力が十分でない場合でも、

```text
不適切な分割
↓
品質ゲート失敗
↓
再設計
```

を繰り返せる。

---

# 17. まとめ

責務境界における基本原則は、

> **所属理由を説明できない処理境界を作らない。**

ことである。

また、

> **複雑度は分割の必要性を示し、モジュール性は分割方法を制約する。**

Complexityを下げるためだけの手続き分割を品質改善とは扱わない。

さらに、

```text
private
↓
public
↓
static
↓
free function
↓
local function
```

のように構文だけを変更した逃避を、個別問題としてではなく、

> **責務を持たない処理境界**

という共通問題として扱う。

この理論を具体的な機械ゲートとして実装する方法は [Quality Guard](./6.2.quality-guard.md) で定義する。
